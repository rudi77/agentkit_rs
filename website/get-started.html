Get started

Run your first task

We will install agentkit, check it with a built-in demo and connect a model. By the end, you can ask it to read a file in your project and explain what it found. The later sections add saved context, external tools and longer-running work.

1. Install

Windows with PowerShell

The setup script downloads a release executable to %LOCALAPPDATA%\Programs\agentkit\bin, adds that directory to your user PATH and creates a configuration template. Run this in PowerShell:

irm https://raw.githubusercontent.com/rudi77/agentkit_rs/main/scripts/agentkit_setup.ps1 | iex

Open a new terminal if it does not yet recognize agentkit. The script also accepts options such as -NoTui, -Version vX.Y.Z, -WithExamples and -Uninstall. The installation reference shows how to pass them.

Windows or Linux release archives

Alternatively, download and unpack the appropriate archive from GitHub Releases, then put its executable on your PATH. Choose the full variant for the terminal UI or the CLI variant for command-line use. Both release variants include context management, PDF reading, graph, work and viewer support.

Build from source

With Rust and Git installed, clone the repository and run Cargo from its root. The crates have separate manifests, so the install path identifies the executable package.

git clone https://github.com/rudi77/agentkit_rs.git
cd agentkit_rs
cargo install --path agentkit_app --bin agentkit --features "tui pdf ctxman tiktoken graph work viz"

Omit tui from the feature list for a build without the terminal interface. scripts/install.sh and scripts/install.ps1 also set up shell completions. Installed builds with update support can be updated using agentkit --upgrade.

2. Check the demo

agentkit --demo "What is 17 + 25?"
agentkit --help

The first command should report 42. Demo mode uses a built-in scripted model and needs no API key. This checks that the executable and tool interaction work; it does not test a model connection or provide general coding assistance.

3. Configure a model

A provider is the service or local server that runs the language model. Choose one of the configurations below. You can set the values in your shell, in a .env file in the directory where you start agentkit, or in the user configuration.

OpenAI through the user configuration

agentkit config init
agentkit config path

The first command creates a template if one does not exist. The second prints its path, normally ~/.agentkit/config.json, or %USERPROFILE%\.agentkit\config.json on Windows. In that file, set the provider and fill in your key and an available model name:

{
  "provider": "openai",
  "openai": {
    "api_key": "<your-api-key>",
    "model": "<model-available-to-your-account>"
  }
}

Replace both placeholders. Values in angle brackets are treated as unset. If the file already contains other settings, edit these fields while retaining any settings you want to keep.

Azure OpenAI through a project .env file

Create a file named .env in the directory where you will run agentkit. Supply the endpoint, key and deployment name from your Azure setup:

AGENTKIT_PROVIDER=azure
AZURE_OPENAI_ENDPOINT=https://<your-resource>.openai.azure.com
AZURE_OPENAI_API_KEY=<your-api-key>
AZURE_OPENAI_DEPLOYMENT=<your-deployment-name>

The deployment name identifies your configured deployment. It may differ from the underlying model name. The configuration template also documents the API-version setting.

A local or OpenAI-compatible server

Start the model server separately and use its compatible endpoint. For example, a local endpoint may be configured as follows in .env:

AGENTKIT_PROVIDER=openai
OPENAI_BASE_URL=http://localhost:11434/v1
OPENAI_MODEL=<model-name-served-locally>

Replace the URL and model name with your server's values. Set OPENAI_API_KEY too if the server requires authentication. Coding tasks need a model and endpoint that support tool calls.

Check what agentkit will use

agentkit config show

This shows effective configuration with masked keys; it does not make a model request. Environment variables override the working directory's .env, which overrides the user config. If an old endpoint keeps appearing, check the higher-priority settings first.

With automatic provider selection, a usable Azure configuration is considered before OpenAI, followed by demo mode. Setting AGENTKIT_PROVIDER or the config's provider makes the selection explicit. Keep files containing credentials out of version control.

4. Read a project file

Open a terminal in a project that contains README.md and run:

agentkit "Read README.md and explain how to run this project. Cite the relevant sections."

The current directory is the workspace. If your project uses another introductory file, name that file instead. You should see tool activity followed by an explanation based on the file. This is your first check of the configured model connection as well as tool use.

To choose a workspace explicitly, use -w. Replace the path in this PowerShell example with your project directory:

agentkit -w "C:\path\to\project" "Read README.md and summarize the setup instructions."

For follow-up questions, start an interactive session:

agentkit --repl
agentkit --tui
agentkit --continue

Choose either the REPL or TUI command. The REPL presents a text prompt; the TUI adds panels and dialogs. Later, --continue resumes the most recent saved session. Inside an interactive session, /context shows context usage and /permissions shows permission rules.

Try a small change

Give the agent a specific change and a way to check it. Shell commands may require approval depending on existing rules. File edits made through the coding tools are checkpointed; /undo restores the latest tracked edit.

agentkit --dry-run "Rename the helper parse_config to load_config and update its callers."
agentkit --verify "Fix the failing test and run the relevant test command."

These are example tasks; use names and a test failure from your own project. Dry run reports destructive tool operations without performing them. Verification prompts the model to check its work; inspect the test result and diff before accepting a change.

5. Use a pipeline

When you pipe a file into agentkit, its contents become context for the task. Print mode, -p, writes the final response without progress output. Create or choose report.txt first.

PowerShell

Get-Content -Raw report.txt | agentkit -p "Summarize the findings in three sentences." | Set-Content summary.txt

Bash

agentkit -p "Summarize the findings in three sentences." < report.txt > summary.txt

To request JSON, use --format json. For example, with a suitable data.json file:

# Bash, with jq installed
cat data.json | agentkit --format json "Return an object with the total in a numeric field named total." | jq .total

JSON output is validated with bounded retries; a run exits with code 4 if it cannot satisfy the requested format. To see progress while keeping JSON on stdout, add --steps and omit -p. When stdin is redirected, agentkit reads until end-of-file, so background scripts must close their input stream.

6. Add context, memory or work tracking

Manage the conversation

--ctx DIR enables managed context and saves its main-agent snapshot. It can move large tool results out of the prompt and summarize older material. Use a separate state directory for independent sessions.

agentkit --ctx .agentkit/ctx --repl

The optional --memory FILE supplies a JSONL recall file. For reusable claims with sources and visibility rules, use the graph instead of treating the entire conversation as project knowledge.

Save and retrieve project knowledge

agentkit --graph .agentkit/graph --repl
agentkit --graph .agentkit/graph --graph-readonly "Find existing notes about configuration loading."

The first command enables graph tools in a conversation. The second reads existing knowledge without enabling graph writes. A new graph has no prior findings; the agent must record them before later tasks can retrieve them.

Create work that can resume

A work project stores items, attempts and output files. This example creates a project named setup-review:

agentkit work create --title "Setup review" --objective "Review the setup instructions, identify missing prerequisites and write an improved guide."
agentkit work run setup-review
agentkit work status setup-review

The create command prints the project identifier; use that identifier in later commands if it differs. Run agentkit work watch setup-review in a second terminal to follow progress. After an interruption, use agentkit work resume setup-review. The journal preserves recorded work state; an interrupted command may already have changed files.

Inspect activity in the browser

agentkit --trace .agentkit/trace "Read README.md and list the documented prerequisites."
agentkit viz --open

Start the viewer in a second terminal or after the task. It opens the trace view on localhost. Use CLI or REPL runs for tracing; the current TUI does not write a trace through --trace.

7. Connect an MCP server

MCP servers are external programs that offer tools. As one example, if uvx is installed and your workspace is a Git repository, save this as .mcp.json in the workspace:

{
  "mcpServers": {
    "git": {
      "command": "uvx",
      "args": ["mcp-server-git", "--repo", "."]
    }
  }
}
agentkit --mcp git "Summarize the recent commits."
agentkit --no-mcp "Read README.md and summarize it."

The first command selects the configured server, which starts as an external process. uvx may need to download its package the first time. The second command disables MCP. A server configuration is executable configuration, and server startup does not pass through the shell-tool approval prompt.

8. Use the Rust library

For a standalone example, create a directory named agentkit-example inside your repository clone, with a src subdirectory. Save this as agentkit-example/Cargo.toml:

[package]
name = "agentkit-example"
version = "0.1.0"
edition = "2021"

[dependencies]
agentkit = { path = "../agent_framework_rs", default-features = false }
serde_json = "1"

Copy the complete Rust example from the agent-loop article into agentkit-example/src/main.rs. From the repository root, run:

cargo run --manifest-path agentkit-example/Cargo.toml

It prints The result is 42. Cargo may need network access to obtain dependencies on the first build, but the example itself uses no model server. It registers an addition tool and uses FakeLlm to script a call followed by an answer.

To connect a real model, enable the core's openai feature and construct a provider with azure_from_env() or openai_from_env(), handling its result. The repository examples show provider and tool setup.

9. Troubleshoot the first run

SymptomWhat to check
The terminal cannot find agentkitOpen a new terminal after installation and confirm the executable directory is on PATH.
Only demo behavior is availableRun agentkit config show. Replace placeholders and check the selected provider.
The wrong endpoint or model appearsInspect environment variables and the working directory's .env; they override user configuration.
The model connects but cannot use toolsCheck that your endpoint and model support tool calls and inspect the reported provider error.
A file is outside the workspaceChoose the intended root with -w, or add a read-only reference directory with --allow-read DIR.
A flag is unavailableCheck --help and the features used to build the executable. The release variants include more features than a minimal source build.
A background command waits without outputEnsure redirected stdin reaches end-of-file.

For the complete reference, see INSTALL.md and the user manual, both in German. The capability guide helps choose what to add next.
