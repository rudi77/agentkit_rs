Architecture

One loop, six crates, one direction

agentkit is a monorepo of loosely coupled components. The agent core is small and stable; everything larger depends on it and never the reverse. This page describes the core from the inside out and then each outer crate and the seam through which it attaches.

The crate map

There is no Cargo workspace at the root. Each crate has its own manifest and its own feature set, and the dependency edges between them are path dependencies that point in exactly one direction:

                 ┌─────────────────────────────────────────────┐
                 │               agentkit-app                  │  the executable:
                 │   (the only crate that knows all of them)   │  CLI · REPL · TUI
                 └───┬─────────┬──────────┬──────────┬─────┬───┘
                     │         │          │          │     │
                     ▼         ▼          ▼          ▼     ▼
              agentkit-swarm  agentkit-graph  agentkit-work  agentkit-viz
                     │         │          │           (reads a file,
                     └────┬────┴──────────┘            links nothing
                          ▼                            from the core)
                       agentkit  ◄──── feature "ctxman" ────  ctxman
                   the loop, tools,                      context management,
                   skills, roles, MCP,                   standalone and sync
                   CLI/REPL/TUI logic

Three facts follow from the picture. The core does not know its siblings. The siblings do not know each other (work reaches the graph through a two-method port that the app implements). And the viewer does not link any of them at all: it consumes the NDJSON trace a run writes, so it neither depends on the core's release cycle nor can it perturb a run.

The loop and its harness

The whole core is Agent::drive in agent.rs. The public entry points — run, run_cb, run_with_events, run_on_bus — are thin wrappers around it that differ only in how they deliver events. The Python original exposes a generator; the Rust port replaces it with an FnMut(AgentEvent) sink, which is the same idea with the control flow inverted.

loop (bounded by max_steps):
    stream = llm.stream(messages)         # 3 retries, exponential backoff,
                                          # Retry-After wins, cancellable while waiting
    for chunk in stream:
        text_delta  -> publish
        tool_call   -> collect
    if no tool calls: publish FINAL, break
    results = run tool calls in parallel  # std::thread::scope; each keeps its own result
    append results; publish tool_result events
    if cancelled: publish CANCELLED, break
publish DONE
save context snapshot (with ctxman: snapshot to disk)

What surrounds the loop is what makes it usable: a step budget; stream retries; a distinction between soft errors (an unknown tool returns Ok("ERROR: …"), the model self-corrects, no error event) and hard ones (a failing tool returns Err and also emits an error event); memory compaction on a token budget; and cooperative cancellation through a shared atomic flag that reaches into a running child process.

The two memory layers are deliberately simple. ShortTermMemory is the message list with a large truncation limit for tool output (16 000 characters, so a coding agent sees whole files and grep results). LongTermMemory is a JSONL recall file. With the ctxman feature, a ManagedContext takes over rendering the provider messages, and the short-term memory keeps running as a mirror for the frontends.

Events decouple everything

The loop publishes typed events: step, text_delta, tool_call, tool_result, plan, final, error, cancelled, done, plus structured for payloads from extension crates and context_snapshot for the end-of-run context of every agent. The type strings are identical to the Python original; the payload is a Rust enum rather than Any.

Every event carries a source. The orchestrator's own events have an empty source; a sub-agent's events are tagged with its role, a swarm member's with its id, a work attempt's with the item and attempt number. That one field is what lets a single bus carry an entire tree of agents, and it is a contract: frontends stop on the first empty-source done, and exit code 2 counts only model failures with an empty source, because a transient failure in one of N helpers must not discard the orchestrator's finished result.

This is why adding a frontend never touches the loop. The CLI renderer, the TUI, sub-agent forwarding, the trace writer and the swarm's event mirror are all subscribers of the same stream.

Tools and the run handle

A tool is a JSON schema plus a Fn(Value) -> Result<String, String>. Rust has no runtime reflection, so schemas are written out explicitly when a tool is registered. The tool function is an Arc, which makes the registry cheap to clone and Send + Sync: that is what allows parallel tool execution and sub-agents that own their own copy of the registry.

The clone has a consequence. A tool that needs the currently active event bus or cancel flag — the task tool, the swarm tool — cannot capture them at registration time, because the registry is copied when the agent is built and the bus does not exist yet. Such a tool holds a RunHandle instead: an Arc-shared cell that drive() overwrites at the start of every run. The rule that follows is small and strict: register the tool before build(), and pass the same handle to the builder.

The coding tools (coding.rs) add two safety nets on top of the registry. Every path goes through a sandbox check that separates read roots from the single write root, and run_shell goes through an approval callback. --dry-run rebuilds the registry with destructive tools replaced by self-reporting no-ops while keeping every schema byte-identical, so the model sees the same toolbox and the loop is unchanged. It is applied to every registry a run creates, not just the orchestrator's.

Sub-agents: one level deep

A sub-agent is not a type. It is an ordinary Agent built from a role — a system prompt, a tool subset and a strategy — and run inside a tool call. The task tool exposes the built-in roles (general, explorer, reviewer, tester) and any custom roles loaded from Markdown files.

Two invariants are enforced structurally rather than checked. Sub-agents never receive the task tool, so delegation is exactly one level deep and cannot recurse. And all agents share one workspace, which is why read-only roles exist and why swarm members default to read-only tools. Parallel task calls in one model response run concurrently and forward their events into the parent's bus.

Strategy: preamble or driver

Strategy has two layers, and keeping them apart is a design constraint from the port. Strategy::{React, Plan, Plain} is nothing but a system-prompt preamble; there is no separate execution path, exactly as in the Python original. On top of it, strategy.rs adds a documented deviation: RunStrategy::PlanExecute is a driver around run_on_bus. It runs a planning phase, then one bounded ReAct pass per step, optionally a reflection with bounded rework, and bounded replanning that replaces the remaining steps. The driver never touches Agent::drive; its phases are source-tagged runs, and it emits the single root final/done itself.

MCP without an event loop

MCP is stdio JSON-RPC, line-delimited. In Rust that needs a Mutex-guarded session and nothing more; there is no asyncio loop to host. Servers come from a .mcp.json in Claude Code format (project level, plus a user-wide file merged underneath), and their tools are namespaced as mcp__<server>__<tool>.

Live enable and disable works by keeping an MCP-free base registry. Applying the hub returns that base; rewiring rebuilds the agent's tools from a clone of the base plus the currently enabled servers and tools. Only an atomic flag flips; sessions are never torn down. Because an MCP server is executed at startup without an approval gate, a name collision that changes the command is surfaced as a warning rather than silently letting a repository-local file take over a name the user trusts.

Frontends are consumers

app.rs holds everything the CLI and the TUI share: building the coding agent, loading .env and the user config, rendering plans, the platform-specific shell hint, the context report. The only real difference between the two frontends is the approval callback — stdin versus a dialog — so it is passed in.

The executable behaves as a Unix filter with the standard streams as its primary adapters: stdin is context, stdout is only the cleaned final result when piped, stderr is everything else. The pipe primitives (exit codes, output format, stdin reading, JSON extraction, outcome classification) live decoupled and tested in cli.rs; argument parsing lives in the binary.

The one extension seam

The core has exactly one extension point: CodingAgentConfig::extra_tools, a closure that receives the registry and an ExtraToolCtx (run handle, model, shared coding tools, MCP hub, skills, roles, dry-run flag) while the coding agent is being built. It exists for one real user, the swarm tool, which the core must not know about. A data field would not have sufficed, because the run handle, the approval callback and (in the TUI) the model only come into existence inside the build function, and two registries cannot be merged. The closure runs before the MCP hub is applied, so an extra tool automatically lands in the MCP-free base registry and survives a live toggle.

The work runtime and the graph reuse the same seam. That is the whole integration story of the outer crates: a closure registers tools, tools carry a run handle, and events flow back through the bus.

ctxman: context as memory

ctxman is a behaviour-faithful port of a C#/.NET service, reduced to its deterministic core and made synchronous. Its mental model is memory management. A static region (system prompt, tool definitions) is epoch-versioned and immutable within an epoch. A working set (messages, tool results, skills) is managed by a garbage collector: clean-page eviction, externalisation into a content-addressed blob store, TTL eviction at unit level (minor GC), and LLM-backed compaction with fact promotion first (major GC).

Two decisions matter most. ctxman never calls the model itself; compaction and promotion run through host-implemented traits, which keeps the library offline-testable and keeps the choice of model with the agent. And the render pipeline is deterministic and byte-stable: the same segment state produces the same provider bytes, which is what keeps prompt caches warm. Golden fixtures from the original pin that behaviour byte for byte, and they are never regenerated to make a test pass.

In agentkit, a managed context renders the provider messages, exposes expand_context_ref as a page-fault tool, and persists a snapshot after every run. Sub-agents and swarm members get an ephemeral variant — GC and externalisation without a snapshot — because most context growth happens in the helpers and a shared state directory would be a correctness bug.

agentkit-swarm: agents as actors

A swarm agent is a normal agentkit::Agent owned exclusively by one actor. The actor adds a mailbox, an identity and peer communication without changing the loop. One actor is one OS thread and one &mut Agent: exactly one message is processed at a time, so there are no mutexes around agents, no nested runs, and a deterministic history per agent. Memory persists across messages; every turn is simply the next user message in a fixed format.

SwarmRuntime (builder → start → monitor → shutdown)
    │  creates mailboxes, hands out permitted ActorRefs, injects tools
    ▼
AgentActor "architect"      AgentActor "developer"      AgentActor "tester"
├── Agent (loop, memory)    ├── Agent                   ├── Agent
├── Mailbox (bounded)       ├── Mailbox                 ├── Mailbox
└── permitted peers ────────┴──── swarm_send / reply ───┘
                                   │
                      swarm_propose / swarm_vote
                                   ▼
                          CompletionActor (counts votes, no LLM)

Two event planes:  agentkit::EventBus → AgentEvents (source = agent id)
                   SwarmEventBus      → SwarmEvents (lifecycle, deliveries, completion)

Topology is a capability: a member that was not handed a reference to a peer cannot send to it, which is stronger than any runtime check. The sender's identity is set by the tool closure, never by the model. Every send path is non-blocking; a full mailbox yields a dead letter; the shutdown reaches every actor through a receive timeout even with a full mailbox. Completion is deterministic — consensus with a voting window, a message budget that brakes rather than kills, an idle timeout — and swarm traffic is mirrored onto existing event types so no frontend needed a change.

The swarm tool is the dynamic variant: the orchestrating agent describes members, prompts, tool access, topology and quorum as JSON. Each member's registry is built from scratch from the coding tools and contains neither swarm nor task. The app can hand members extra tools (the graph, notably) through extra_member_tools, a closure that receives the member id so a tool knows its true author.

agentkit-graph: knowledge with provenance

The graph stores knowledge; peer messages request actions; what reaches the model's context is decided by recall, never by the graph itself. The model is entities, claims (subject–predicate–object with status, confidence and sources), sources and episodes, on two orthogonal axes: a layer — working or canonical — and a scope that says who owns it. Visibility runs exclusively through scope.

Reader A ─┐                       ┌─ Arc<GraphIndex> (revision 41)
Reader B ─┼─ store.snapshot() ────┤   immutable, traversed lock-free
Reader C ─┘                       └─ …

Writer ── OKF bundle on disk ── new index ── Arc swap (revision 42)

Readers hold a lock only for the duration of an Arc clone and then traverse an immutable snapshot. Writers commit synchronously: disk first, then the swap. A receipt therefore means the mutation is visible to every reader, and read-your-writes needs no queue, no writer actor and no revision timeout. The revision is a store-wide monotonic number that serves as mutation id, audit mark and recency signal at once.

On disk the graph is an Open Knowledge Format bundle: one Markdown document per entity with YAML frontmatter, layer and scope encoded in the directory path, everything graph-specific under a single extension key. There is no storage dependency and no C compiler; a minimal YAML adapter keeps it pure Rust. Frontmatter is the truth and the body is decoration, so a human may edit the prose without endangering a rebuild. Claim status moves observation → hypothesis → confirmed → superseded; only promotion can confirm, and a model cannot canonicalise its own claims.

agentkit-work: state that outlives the agent

The premise of the work runtime is that an agent does not need to live for hours; the work state does. A WorkProject holds items with dependencies, acceptance criteria and a verification policy; a WorkRun executes them with a synchronous single-worker loop that builds a fresh agent per attempt through the ordinary coding-agent builder and registers its own tools through the extension seam. Item identity — run, item, attempt, agent — is set by the runtime and has no tool argument.

Storage is an in-memory state behind a read-write lock plus an append-only JSONL journal whose compaction is the checkpoint: a snapshot line is appended, the history stays intact, and reopening replays only the events after the last snapshot. Ready and Blocked are derived views, not stored states, so they cannot drift from the dependency graph. Recovery completes half-written transitions rather than discarding them, an interrupted attempt does not count as a failed one, and a lock file (created atomically, removed on drop, never auto-cleaned by PID guessing) prevents two workers from corrupting one journal.

Verification is a property of the item: none, an automated command run without a shell, an independent read-only reviewer item spawned automatically (itself unverified, to avoid infinite regress), or human approval. The graph is reached through a two-method port, recall and record_claims, that lives in the work crate and is implemented by the app.

agentkit-viz: the trace is the seam

The viewer consumes nothing from the agent side. It reads the NDJSON trace a run writes and defines its own mirror types with owned strings, so an unknown event variant is kept with its raw form instead of being dropped. Inside, it is hexagonal: model, project and swarm are the domain with no HTTP and no filesystem; trace and server are the adapters. The projections are tested without a server.

The server is single-threaded, polls instead of streaming (a documented deviation from the original plan, chosen because server-sent events would have cost a thread per connection and a hand-written HTTP frame), binds only to loopback, checks its random token before touching the filesystem, and has no writing endpoint. tiny_http is the only foreign crate it adds, and it stays behind the viz feature.

agentkit-app: where the crates meet

The executable crate exists because a binary inside the core would create a Cargo package cycle: the swarm depends on the core, and the executable needs both. So the app is a thin wiring crate with no domain logic. It parses arguments, renders the event stream, and injects the swarm and graph tools through the extension seam, hands the work CLI a model builder and an approval callback, and dispatches agentkit viz. It is the only place where the graph is adapted to the work runtime's port, because it is the only crate that knows both.

One deliberate deviation lives here: the release profile keeps panic unwinding instead of aborting, because the swarm supervisor detects an actor panic through a failed thread join and shuts the swarm down in a controlled way. With panic = "abort" the whole process would die instead.
