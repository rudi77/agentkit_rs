Architecture

From a request to a result

This guide follows a task through agentkit, then shows how the surrounding libraries connect to it. We begin with the model and tools because every execution mode uses that exchange. A crate is a Rust package; you can treat the crate map as a guide to where each responsibility lives.

1. Running the model and tools

Imagine a task that asks the agent to explain a function. The model may first request read_file. agentkit runs that tool, adds the file contents to the conversation and calls the model again. The second response can use the code it has now seen.

task + conversation + tool definitions
                  |
                  v
             model response
                  |
          requests any tools?
           /             \
         yes              no
          |                |
     execute tools     final answer
          |
     append results
          |
     call model again

Agent::drive and drive_inner coordinate this process. Public methods such as run, run_cb, run_with_events and run_on_bus provide different ways to receive results and events from it.

The loop also has a step limit, model-stream setup retries and a shared cancellation flag. Cancellation is cooperative: the runtime and supported tools check the flag at defined points. Several tool calls from one response can run on scoped threads when parallel execution is enabled. Their results remain associated with their respective calls.

A failed request needs feedback the model can use. For example, an unknown tool produces an ERROR: … result. A tool implementation that returns an error also produces an error event. Those cases differ from a model connection failure, which the stream setup code handles with bounded retries and backoff.

2. Reporting progress through events

The runtime reports activity as AgentEvent values. Consumers decide how to display or save them. This lets the terminal show streamed text while the trace writer records tool calls from the same run.

EventMeaning
step, text_deltaA model step began, or another piece of response text arrived.
tool_call, tool_resultA tool was requested, or a result became available.
plan, structuredA plan changed, or an extension published a structured payload.
final, error, cancelled, doneAn answer, failure, cancellation or end of a run was reported.

The source field identifies whose activity an event describes. An empty source denotes the main agent; helpers and work attempts use labels. A consumer must therefore distinguish a helper's done from completion of the main run. Context snapshots travel as structured payloads with a kind of context_snapshot.

3. Registering tools

The tool registry associates a name and JSON schema with a Rust function. The schema describes arguments for the model; the function validates the values it needs and performs the operation. Its signature is Fn(Value) -> Result<String, String>.

Tool functions are shared through Arc, Rust's reference-counted shared ownership type. A cloned registry can therefore share callable tools without copying their implementation. Tools that operate on shared data still need appropriate synchronization.

Some tools need access to the current run. A delegated task, for example, must forward events to its parent and respect cancellation. These tools capture a RunHandle, a shared object updated at the start of a run with the active bus and cancellation flag. Register such a tool before building the agent, and pass the same handle to the builder.

Coding tools add workspace checks for file access and an approval callback for shell commands. These are separate controls: checking a file path does not restrict every effect of a shell command. Dry-run construction replaces destructive operations with reporting no-ops while preserving their tool schemas.

4. Delegating a task

The task tool builds an ordinary agent with a role-specific prompt and tool set. For example, an explorer can read relevant files and return a summary to the parent. The explorer's full conversation stays in its own context; the parent receives its result.

Roles include general, explorer, reviewer and tester, with additional roles loaded from Markdown. The helper does not receive the task tool, which limits delegation to one level. Agents share the workspace, so selecting read-only roles is useful when several helpers investigate at once. See sub-agent construction and role definitions.

5. Choosing an execution strategy

react, plan and plain select system-prompt preambles. They guide the model while using the same execution loop. ReAct here refers to alternating model responses and tool use.

plan_execute adds a driver around agent runs. It obtains a plan, executes steps as bounded passes and can use reflection and bounded replanning. This involves more model interaction. Its phases have source labels, and the driver emits the final events for the overall task. The distinction is implemented in strategy.rs.

6. Connecting MCP tools

Model Context Protocol (MCP) provides a way for an external program to offer tools. agentkit's MCP client communicates with those programs using JSON-RPC messages over standard input and output. A mutex serializes access to each synchronous session.

Servers are configured in .mcp.json. Their tools receive names such as mcp__git__git_status, keeping server names separate from built-in tools. The user configuration is merged with the project configuration; a project entry that changes a same-named command produces a warning.

To support live enable and disable, agentkit keeps a base registry without MCP tools. It rebuilds the active registry from that base and the enabled MCP tools, retaining existing server sessions. Configured servers can start external processes during initialization; shell-tool approval is not an approval gate for MCP startup.

7. Terminal interfaces

The one-shot CLI, interactive REPL and terminal UI share agent construction and event handling components. They differ in how they accept input, display progress and obtain approvals. The REPL is a repeated prompt; the TUI adds panels and dialogs.

For pipelines, standard input supplies task context, standard output carries the final result and diagnostic output uses standard error. Print mode suppresses progress output. Argument parsing and command dispatch live in the app binary; reusable output handling lives in cli.rs.

8. Adding tools from another crate

The coding-agent builder accepts CodingAgentConfig::extra_tools, a callback that receives the registry and an ExtraToolCtx. It runs while the agent is being built, when the model, run handle and shared coding tools are available.

The app uses this callback to install tools supplied by other crates, including swarm and graph tools. The callback runs before MCP is applied, so these tools become part of the base registry and survive later MCP toggles. This is the coding-agent builder's integration point; the core also exposes ordinary tools, model traits and event APIs for library users.

9. Managing model context

ctxman prepares the material sent in a model request. It separates relatively stable material, such as the system prompt, from changing messages and tool results. As the working material grows, policy thresholds trigger operations that reduce its size.

Large results can be stored as blobs and replaced in the prompt by shorter representations and references. expand_context_ref retrieves saved content when needed. More extensive compaction uses a model to summarize older material and can promote facts to long-term memory first. The host supplies that model through an interface, so ctxman itself does not choose a provider.

The same segment state renders deterministically, which avoids unnecessary changes to request text and can help with provider prompt caching. Cache use still depends on the provider. Main-agent snapshots support later sessions; helpers receive temporary managed contexts without shared snapshot directories. See ctxman for policy details and reference fixtures.

10. Exchanging messages in a swarm

An actor owns an agent, a thread and a bounded mailbox. It processes one incoming message at a time, so that agent's conversation is updated sequentially. Different actors can work concurrently.

architect                     tester
Agent + mailbox               Agent + mailbox
      |                             |
      +------ peer messages --------+
      |                             |
      +---- proposals and votes ----+
                    |
             completion policy

Peer references determine which members can communicate. A send tool supplies the sender identity from the actor that owns it. Ordinary peer sends are non-blocking; if a mailbox is full, the runtime reports an undelivered message, called a dead letter. The initial task delivery uses a separate blocking send path.

Completion may follow a voting quorum, idleness, a delivery budget or a time limit. The voting window lets the runtime count support for proposals; it does not evaluate their truth. Dynamic swarms build member registries without task or swarm, preventing recursive creation through those tools. The app can add graph tools to each member. See the swarm implementation guide.

11. Storing project knowledge

The graph stores entities and claims about them, together with sources and records of activity. For example, a claim can connect a module to the configuration format it reads. Its source records where that information came from.

Two fields answer different questions. The layer separates working material from canonical, durable knowledge. The scope controls the workspace, session, swarm or agent context in which material is visible. Promotion checks govern whether a working claim can become canonical; changing a prose description alone does not confirm it.

The store writes an Open Knowledge Format bundle of Markdown documents with structured frontmatter. Readers obtain an immutable index snapshot. A successful write commits to disk and publishes a new snapshot for subsequent readers; a reader already holding an older snapshot continues to see that older revision. Index rebuilding and in-memory storage impose scaling limits described in the graph README.

12. Tracking work across attempts

A work project contains items with dependencies and acceptance criteria. An attempt is one execution of an item. The worker selects eligible work and creates an agent for the attempt, carrying forward artifacts from completed predecessors.

State changes are appended to a JSONL journal: one JSON record per line. Checkpoints let reopening begin from a saved state and replay subsequent events. A lease records ownership of active work, while a lock file prevents competing writers from running the same project.

Recovery uses these records to handle interrupted attempts. It preserves recorded progress but does not roll back arbitrary filesystem changes or external command effects. Verification policies can request a test command, an independent reviewer or human approval. A successful attempt and an accepted result are therefore separate states when verification is configured.

Work accesses the knowledge graph through GraphGateway, an interface implemented by the app. The work crate does not import the graph crate. The work README describes recovery, verification, optional Git isolation and the execution strategies.

13. Reading traces and saved state

The viewer reads the trace file written by a supported run. It defines its own trace types and preserves unknown event payloads so that unfamiliar events can still be inspected. Its browser interface polls a synchronous HTTP server on 127.0.0.1.

With the corresponding features enabled, the viewer also imports agentkit-graph and agentkit-work to read their saved state. The trace is the source for agent activity; the graph and work panels use their read-only store APIs. A startup token restricts access to the local server, which exposes no mutation endpoints. See viewer behavior and limitations.

14. Building the executable

agentkit-app connects the libraries, handles command-line arguments and supplies adapters such as the work-to-graph integration. Keeping the binary here avoids a dependency cycle between the core and libraries that extend it.

Its release profile retains panic unwinding so that the swarm supervisor can observe an actor thread failure through a failed join. Aborting the entire process on a panic would prevent that recovery path.
