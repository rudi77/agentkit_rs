Design principles

The reasons behind the implementation

The design guidelines aim to keep agentkit understandable as it grows. This page explains how they affect actual code, where they introduce tradeoffs and what contributors should check. The repository guidelines remain the full contribution reference.

On this page
  1. Make the execution path visible
  2. Introduce interfaces for a concrete need
  3. Use concurrency where it helps
  4. Define ownership and access
  5. Preserve observable behavior

Make the execution path visible

A reader investigating a tool failure should be able to follow the model request, tool execution and error handling in order. The agent driver coordinates named steps for that reason. Smaller private functions are useful when they make a step easier to understand and test.

The same preference applies to strategies. react, plan and plain need different prompt preambles, so they share an execution path. plan_execute needs additional planning and execution phases, so it has a driver that calls ordinary agent runs. The amount of structure follows the behavior being implemented.

There is no fixed line-count target for a function. The review question is whether its responsibility and state changes can be understood together. Splitting a function should make that understanding easier.

Introduce interfaces for a concrete need

An interface is useful when the application needs to substitute one implementation for another. The model interface, for example, supports both a provider client and a scripted test model. ctxman delegates compaction to a host-supplied model, which lets the host choose the provider and lets tests supply predictable results.

The guidelines ask for concrete uses before adding abstraction. When an interface is justified, it should cover the operations its callers need. The work runtime's GraphGateway exposes recall and claim recording; it does not need to expose the graph's storage implementation.

This also explains why storage choices can remain concrete. The current graph uses Markdown bundles and the work runtime uses a JSONL journal. A hypothetical second backend is not enough reason to make every operation generic today. These file-based designs are inspectable, but the graph's in-memory index and rebuild-on-write behavior place limits on scale.

Use concurrency where it helps

agentkit uses synchronous model calls. Concurrent tool calls use scoped Rust threads, and each swarm actor owns a thread and processes one message at a time. That ownership makes it clear which execution can mutate an agent's conversation.

Synchronous code is straightforward to trace, but blocking calls occupy threads. The design does not imply that threads are the best choice for every server workload. In agentkit, concurrency is introduced for actual tool and actor workloads, with budgets and bounded mailboxes to limit them.

Dependencies are treated in the same way. Model connectivity is behind features, and the viewer uses a small synchronous HTTP server for its local UI. Offline execution and testing remain available without requiring every build to have an identical dependency set.

Define ownership and access

Suppose a swarm member sends a message. The sender identity comes from the runtime object captured by its tool, so the model does not need to supply a from argument. Graph and work tools similarly receive their author, access scope or attempt identity from the runtime.

Tool selection can also enforce a limit directly. A sub-agent does not receive task; a dynamic swarm member receives neither task nor swarm. Those agents cannot recursively delegate through tools they do not have.

Other boundaries require explicit checks. File tools validate workspace paths, and graph promotion checks visibility and evidence. These mechanisms protect specific operations; they do not establish the correctness of a model's claims or restrict every effect of an approved external command.

Dependencies keep responsibilities separate too. The agent core does not import swarm, graph or work. The app supplies their integration. The viewer reads traces and, when enabled, uses graph and work reader dependencies. The crate map shows the current relationships.

Preserve observable behavior

Changing an event name or exit code can break a caller even if the agent still returns the same answer. The CLI's output streams, event source labels and saved formats therefore form part of the behavior that changes must account for.

The core originated as a Rust port of a Python implementation; ctxman originated as a port of a C# service. Their references help explain existing choices. Deliberate deviations belong in the relevant README so a later contributor can distinguish a conscious change from an accidental mismatch.

Keep refactoring and behavior changes separately reviewable. When an observable contract must change, identify the consumers that need to change with it.

Explain decisions in the documentation

API documentation should tell a caller what happens: how errors are returned, when events arrive and which state an operation changes. Comments should explain reasons that are difficult to infer from the code alone.

For example, a comment beside RunHandle should explain why a tool needs the current run's bus after registration. Repeating that the code clones a handle contributes less than explaining the lifetime problem that the handle solves.

User guides need another starting point: the reader's task. Introduce a term when it becomes necessary, show an example and explain the result. If an example uses a scripted model, say so. If resuming work preserves a journal but cannot reverse command effects, state that distinction where recovery is introduced.

The repository uses German for documentation and user-facing text, with English identifiers and wire values. This public website uses English for its broader audience.

Measure the relevant cost

A benchmark with a scripted model measures framework overhead without network or model latency. It is useful for comparing implementations of the loop. It cannot establish how quickly a real coding task will finish or how often its answer will be correct.

Before optimizing, identify the cost that matters for the workload: prompt size, repeated file reads, tool execution, model latency or local bookkeeping. Report the setup and limits with the result. Small allocation improvements may be reasonable during normal coding, but more complicated changes need evidence that justifies them.

The core README documents its benchmark comparison. The separate benchmark harness evaluates the executable on coding and terminal tasks. These measurements answer different questions.

Make behavior testable offline

A scripted model can request a known tool and then return a final answer. A test can inspect the tool result, event sequence and cancellation behavior without waiting for a provider. It verifies the runtime under that sequence, rather than predicting how a model will behave on arbitrary tasks.

ctxman's golden fixtures compare output with saved reference data. A byte difference may indicate a change to rendered requests or another behavioral contract. Understand that change before updating a fixture; regenerating the expected output alone is not an explanation.

Use existing interfaces such as the model and event sink to isolate behavior. A useful test describes an externally meaningful case, including failure paths that would otherwise be hard to reproduce.

Before submitting a change

  • Explain the behavior and why the chosen structure is needed.
  • Check affected events, output formats and persisted state.
  • Document deliberate differences from a port or design reference.
  • Run the relevant offline tests and investigate changed fixtures.
  • Support performance claims with the workload and measurements.
