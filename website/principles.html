Design principles

Simplicity is a feature

agentkit is governed by a short, binding set of coding guidelines, and by a handful of conventions that every crate in the repository shares. They are not aspirations; they are the review checklist. This page states them in the form in which they actually shape the code.

The best code is the code that is never written. The second best is code you can read once, top to bottom, and understand.

1. Simplicity first

Direct, procedural code beats indirection. A function that makes its flow visible is better than three layers that hide it. No design pattern for the pattern's sake. When there is a choice between a clever solution and a boring one, the boring one wins.

The canonical example in the repository is Strategy: ReAct, Plan and Plain are nothing but a system-prompt preamble. It would be easy to "abstract that properly" into a trait hierarchy with its own execution paths. It is not, because the preamble is all that is needed.

2. Abstraction only on proven need

The rule of three: abstract at the third concrete user, not at the first imagined one. A trait needs at least two real implementations to exist. Llm has the OpenAI client and the fake model used in tests; ctxman's CompactionModel and BlobStore have their real and their test implementations. A trait with one implementation "for later" is folded back into a concrete type.

When abstraction is warranted, it goes at the narrowest point: small, synchronous traits with few methods, not wide interfaces that pass everything through. Generics only where they carry real value, such as the FnMut(AgentEvent) sinks.

The knowledge graph illustrates the discipline. Its product requirements sketched reader, writer and resolver traits and backend abstractions for Postgres and Neo4j. None of them exist; they are concrete types and functions, and a second backend trait will be introduced when the second backend does.

3. Single responsibility

One module is one topic; one function is one step. The rule of thumb: if a function cannot be described in a sentence without "and", split it. Orchestrating functions call named steps instead of carrying domain logic inline. But single responsibility does not mean a new file and a struct hierarchy per responsibility: a private function in the same module is the preferred first level of separation, and a topic gets its own module only when it grows. There are no dogmatic line-count limits; the criterion is whether a block can be understood and tested in isolation.

4. No over-engineering

  • No configurability without a concrete second use case. Every builder option and every flag must cover a real need.
  • No new dependency without necessity. The offline, zero-TLS default of every crate is a feature; each dependency must respect it behind a feature gate and earn its place. The graph and the work runtime chose a Markdown bundle and a JSONL journal over SQLite precisely to keep a C compiler out of the repository and out of the static musl build.
  • No async runtime, no channels or threads "in reserve". Concurrency only where it is needed today: scoped threads for parallel tools; one thread per actor in the swarm, because the actor model is the non-reentrancy argument.
  • Error handling in proportion: soft errors as values (Ok("ERROR: …")), hard errors as Err, no custom error hierarchies while strings and small enums suffice.

5. Readability and documentation

Comments explain the why and the invariant, never the what. A good comment states a reason the code cannot show on its own — "overwritten at the start of every run, so an explicit reset is unnecessary because…". Doc comments on public APIs document behaviour and contracts: error contract, event order, edge cases. New code reads like the surrounding code: the same comment density, the same idioms, the same naming.

Everything user-visible in the repository is German — doc comments, prompts, tool descriptions, CLI output, READMEs, commit messages. Identifiers and wire values are English. That convention is why a tool result reads zugestellt while a claim status reads confirmed: the model must echo the latter verbatim.

6. Maintainability

Port fidelity. agentkit is a structural one-to-one port of a Python original; ctxman is a port of a C# service. Before any restructuring, the counterpart is checked. Deviations are made deliberately and recorded in the respective README's "deliberate differences" section, never silently. The crates that are not ports — swarm, graph, work, viz — keep an equivalent section of design decisions, including every deviation from their own product requirement or plan.

Behavioural contracts are API. Exit codes, event type strings, the stream and stdin behaviour of the CLI, the failure sentinels a run returns, ctxman's golden fixtures. They are never changed casually; the benchmark harness, the frontends and the sibling crates depend on them.

Small, traceable changes. One refactoring step per commit; behaviour change and restructuring never in the same commit.

7. Performance

Measure before optimising. There is a bench binary for framework overhead; speculative optimisations without a measurement are not merged. Basic hygiene is free and expected — no needless clones in hot paths, Arc where things are shared, allocations pulled out of loops when readability allows — but readability beats micro-optimisation, and an optimisation that complicates the code needs a measurement that justifies it, recorded in a comment or the commit.

The same rule applies to design claims. The tool-result lifetime in the context policy was raised from the spec's value after counting repeated file reads in a benchmark trace. The delegation prompt was rewritten after observing which of two contradictory instructions a model actually followed. The trace cache in the viewer engages only when a directory walk measured expensive.

8. Testability

Every new capability is testable offline. In agentkit that means scripting the fake model with the chunk sequence a real model would have produced; in ctxman it means the orchestration tests, which read as the behavioural specification, and the golden fixtures, which are byte-exact and are never regenerated to make a test pass. No test touches the network, and that stays so.

A test checks one behaviour and reads as a specification. Testability is the one legitimate reason to introduce an abstraction earlier than rule 2 allows, but through the existing seams — the model trait, the fake model, the event sink — never through new mock frameworks or extra indirection in production code.

Conventions that cut across the crates

Beyond the guidelines, a few architectural conventions recur so consistently that they deserve to be named.

Dependencies point one way

The core does not know the swarm, the graph or the work runtime. They depend on it. The siblings do not know each other; where one needs another, it declares a small port and the executable crate implements it. The viewer depends on none of them and reads a file instead.

Identity is set by the runtime, never by the model

No tool that writes to shared state has an argument for who is writing or where. A swarm member's from is set by the tool closure. A graph writer's author, run and scope live in an access object captured at registration. A work attempt's run, item, attempt and agent ids have no tool parameter. The claim-recording tool builds provenance from the running context. These are structural facts: a model cannot impersonate a peer, write into a foreign scope, or canonicalise its own hypothesis, and no validation code has to be right for that to hold.

Limits are structural, not validated

Sub-agents do not receive the task tool, so there is no recursion. Swarm members are built from a fresh registry without swarm or task. Topology is a capability: no reference, no send. File names in the graph bundle come from a whitelist of characters, so a path escape is impossible rather than checked for. An empty sandbox root is discarded at construction, not by every caller.

Soft errors are values the model can read

An unknown tool, a malformed swarm specification, a full mailbox, a rejected delivery: each comes back as a string or a status value that the model sees and can act on. Hard errors are reserved for the cases where continuing would be wrong. Timeout messages name their remedy, because an error the model cannot act on is a dead end it will retry.

Limits are named honestly

The graph lives entirely in memory and rebuilds its index on every commit, and the README says at what size that stops being fine. The viewer re-reads the whole work journal on every tick, and says so. The work runtime has no token budget because the core cannot measure one. Where a capability is missing, the documentation states it under "not in scope" rather than leaving it implied.

The review checklist

  1. Could this work just as well with less code or abstraction?
  2. Does every new abstraction have two real users today, or the testability reason from rule 8?
  3. Can every new or changed function be described in one sentence without "and"?
  4. Are there why-comments where the code cannot show an invariant itself?
  5. Python or C# counterpart checked, deviation documented?
  6. Behavioural contracts — events, exit codes, fixtures — untouched?
  7. Offline tests green, new capability covered with the fake model?
  8. Performance claims measured rather than assumed?
