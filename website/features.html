Features

What agentkit does

agentkit is two things at once: a library for building agents, and a finished coding agent you install and run. The list below covers both. Each capability is designed so that it can be tested offline, switched off, or left out of a build entirely.

The agentic loop

The core is a single streaming loop: the model is asked, its answer is streamed, every tool call in the answer is executed, the results are appended, and the model is asked again until it stops calling tools. Around that loop sits a harness that makes it fit for real work:

  • Streaming and typed events. Every step, token delta, tool call, tool result, plan update, final answer, error and cancellation is published as an AgentEvent. Frontends, sub-agent forwarding and the trace writer all consume the same stream.
  • Parallel tool calls. When the model requests several tools in one response, they run concurrently on scoped threads, and each call keeps its own result.
  • Retries with backoff. Stream setup is retried three times with exponential backoff. If the provider sends Retry-After, that value wins (capped at 60 seconds), so a rate limit is waited out rather than hammered.
  • Soft errors as values. An unknown tool or a bad argument returns an ERROR: … string that the model reads and corrects. Only a genuinely failing tool raises an error event.
  • Cooperative cancellation. A shared stop flag is checked between steps, while waiting on a retry, and inside a running shell command, which is killed immediately.
  • Step budget and compaction. max_steps bounds a run; a token budget triggers summarising compaction of the short-term memory when no context manager is attached.
  • Long-term memory. A JSONL recall file the agent can write to and read from across runs.
  • Session persistence. The full conversation is saved as JSON after every task and reloaded on start, so one-shot chains, the REPL and the TUI can resume across process boundaries. Terminal sessions are managed automatically; --continue and --resume pick them back up.

Coding tools and safety

With a real model configured, the agentkit executable is a full coding agent. Its tools are deliberately few and deliberately fenced:

  • Sandboxed file tools. list_files, glob_files, grep, read_file, read_pdf, write_file, edit_file. Every path is confined to the workspace; additional read-only roots can be granted with --allow-read without widening the write sandbox.
  • Approved shell. run_shell goes through an approval callback: a prompt on stdin in the CLI, a dialog in the TUI. Approvals can be remembered per program for the session or permanently; a blanket "allow everything" is only ever -y and is never persisted.
  • Read-only git tools. git_status, git_diff, git_log, git_show with structured arguments, so reviewer roles can see history and diffs without shell approvals.
  • Checkpoints and /undo. The previous state of a file is saved before every write or edit. /undo reverts the latest change, /undo all everything. Sub-agents and swarm members write to the same shared stack.
  • Project instructions. AGENTS.md in the workspace (and a personal one in the config directory) is appended to the system prompt. Its optional frontmatter carries deny/allow guardrails for the shell that hold even under -y.
  • Dry runs. --dry-run keeps every tool schema identical but turns destructive tools into no-ops that report themselves, in the orchestrator, in every sub-agent and in every swarm member.
  • Self-verification. --verify nudges the model once to run a check after editing files before it declares itself done, a pattern that came straight out of benchmark failure analysis.

Sub-agents and roles

The agent has one task tool in the style of Claude Code. It takes a subagent_type: general, explorer, reviewer, tester, or any custom role loaded from a Markdown file (frontmatter is metadata, the body is the system prompt). A role is pure data: a prompt, a tool subset and a strategy.

  • Exactly one level deep. Sub-agents never receive the task tool, so there is no recursion. The same rule applies to swarm members.
  • Parallel by default. Multiple task calls in one model response run concurrently and forward all their events into the parent's bus, tagged with a source.
  • Delegation as the default. The coding prompt steers the orchestrator to delegate reading to an explorer; if it reads four or more files itself in one run, a single nudge reminds it. What a sub-agent reads stays in the sub-agent's context.
  • Custom teams from data. The coding_swarm example builds a tech lead with architect, developer, tester and reviewer roles entirely from Markdown, no framework code.

Strategies

react, plan and plain are system-prompt preambles only, faithful to the Python original. plan_execute is a real driver that wraps the unchanged loop: a planning phase produces a step list, each step runs as its own bounded ReAct pass, an optional reflection may ask for rework, and bounded replanning replaces the remaining steps if the plan turns out to be wrong. Each phase shows up as its own source-tagged event stream.

Skills and MCP

  • Skills with progressive disclosure. Skill directories are listed by name and description; the model reads a skill's body only when it needs it. Skill collections written for Claude Code work as they are: YAML block scalars, ${CLAUDE_SKILL_DIR}, $ARGUMENTS and Claude Code tool names are all understood.
  • MCP over stdio, synchronously. Servers are declared in a .mcp.json in Claude Code format and discovered automatically. Their tools appear as mcp__<server>__<tool>. A user-wide config is merged underneath the project config, and a name collision that changes a command is surfaced as a warning.
  • Allowlists at two levels. --mcp NAME restricts active servers; a per-server tools list restricts which of its tools cost schema tokens. Both are toggled live in the REPL (/mcp) and the TUI (F2) without tearing down a session.

CLI, REPL, TUI and pipelines

All three frontends are consumers of the same event stream; the only real difference between them is how they ask for shell approval.

  • One-shot and REPL. agentkit "task" streams an answer; agentkit --repl keeps memory across turns with a real line editor (history, reverse search, multi-line input, tab completion for slash commands and @paths), Markdown rendering of the streamed reply, and slash commands for context, tools, sessions, rewinding, forking, compaction and export.
  • TUI. A ratatui terminal UI with live steps and tokens, an in-UI approval dialog, a permission-mode toggle, an MCP panel, queued type-ahead while a task runs, and /context for a colour-coded picture of what occupies the model's context, for the main agent and for every sub-agent and swarm member.
  • A proper Unix filter. stdin is context, stdout is only the cleaned final result when piped or in -p/--format json mode, stderr is everything else. Exit codes are a contract: 0 ok, 1 runtime error, 2 API/network, 3 context too large or prompt invalid, 4 --format not satisfiable. -- ends options, unknown options are reported, and broken pipes end cleanly.
  • Per-stage profiles. --profile FILE bundles system prompt, strategy, tools, skills, MCP allowlist and more as JSON, so a pipeline becomes a chain of clearly separated agents.
  • Structured output. --format json switches on the provider's JSON mode plus validation with retries.
  • Everyday ergonomics. Shell completions for bash, zsh, fish and PowerShell; --notify for a terminal bell when a long run finishes; --model to override the model; agentkit --upgrade to update the installed binary; agentkit read-pdf as a deterministic, token-free text extractor.

Context management

Naive compaction is lossy and eventually throws away something relevant. With the ctxman feature (on in all release builds), --ctx DIR hands context management to a garbage collector modelled on memory management:

  • Watermarks instead of a hard limit. At 60 % of the budget a minor GC externalises large tool results losslessly into a content-addressed blob store, leaving a summary and a reference in context. At 80 % a major GC runs LLM compaction with fact promotion first, so durable facts land in long-term memory before the summary is written.
  • Page faults. The expand_context_ref tool lets the model pull an externalised result back in full when it needs it.
  • Snapshot resume. The whole context, blob references included, is persisted; a restart continues exactly where it stopped, with the policy frozen for the session.
  • Kind-aware lifetimes. Tool results live 12 turns (measured against benchmark traces: repeated re-reads of the same file were the dominant waste), skill bodies are refetchable and expire, sub-agent results are pinned because they are expensive to reproduce.
  • Byte-stable rendering. The same segment state always renders to the same provider request bytes, which is what keeps prompt caches warm. Conformance is pinned by golden fixtures from the C# reference.
  • Accurate counting and a cheaper compaction model. With the tiktoken feature the tokenizer is real (o200k or cl100k), and --ctx-compaction-model routes summarisation to a smaller deployment.
  • Helpers get it too. Sub-agents and swarm members receive an ephemeral managed context: watermark GC and externalisation without snapshots, because most context growth happens in the helpers.

Swarms

agentkit-swarm turns ordinary agents into actors. Each agent is owned exclusively by one OS thread with one bounded mailbox; agents talk peer-to-peer through six tools (swarm_peers, swarm_send, swarm_reply, swarm_broadcast, swarm_propose, swarm_vote) and nobody touches anybody else's state.

  • Deterministic completion. A swarm ends on consensus (a counted quorum with a voting window so the best-supported proposal wins, not the fastest), on a message budget, on idleness, or on an optional wall-clock limit. Never "semantically".
  • Topology as capability. A member can only send to peers it received a reference for. Mesh, chain and star presets, or explicit connections.
  • Rejections go back to the author with the critique, so a "no" is a round, not a dead end.
  • Deadlock-free by construction. Every send is non-blocking; full mailboxes produce dead letters; nothing is lost silently.
  • Built at runtime. The swarm tool lets the coding agent describe members, prompts, tool access, topology and quorum as JSON and blocks until the result is in, with hard limits (at most 6 members, 300 deliveries, 900 seconds, 40 steps per member) and no recursion.

Knowledge graph

agentkit-graph gives agents a memory that lasts across sessions and across members of a swarm. Entities, claims (subject–predicate–object with status, confidence and sources), sources and episodes live on two axes: a layer (working or canonical) and a scope (workspace, session, swarm, agent).

  • Five tools. graph_search, graph_neighbors and graph_evidence to read; graph_remember to record observations and hypotheses; graph_promote to move a sourced claim into durable knowledge. A model cannot canonicalise its own claims and cannot choose its scope or author.
  • Lock-free reads, synchronous writes. Readers traverse an immutable snapshot; a write commits to disk first and then swaps the snapshot, so read-your-writes is a fact rather than a feature.
  • Provenance that survives compaction. Promotion records where a claim came from and what status it had, on the record itself. Contradicting canonical claims are superseded, never overwritten.
  • Plain files. Storage is an Open Knowledge Format bundle: one Markdown document per entity with YAML frontmatter, readable, diffable and valid for any OKF consumer. Zero storage dependencies.
  • Automatic recall. --graph DIR prepends a small, budgeted, deterministic slice of relevant claims to each task, for the orchestrator and for every dynamically created swarm member.

Work runtime

agentkit-work is for undertakings that run longer than one agent run. The premise: agents may be short-lived, but the work state must live for hours.

  • Projects, runs, items. agentkit work create|run|status|watch|resume|list|events|budget. A project is decomposed into work items with dependencies and acceptance criteria; a single synchronous worker executes them in dependency order, building a fresh agent per attempt.
  • Leases, attempts, artifacts. Every attempt renews a lease from inside the agent's event callback; artifacts land in the workspace under artifacts/<item>/<attempt>/, so the next agent reads them with the ordinary read_file tool.
  • A journal, not a database. Every state change is an event in append-only JSONL; a checkpoint is an appended snapshot line, so resume is O(events since checkpoint) and the timeline stays intact. Recovery completes half-written transitions instead of discarding them, and an interrupted attempt does not count against the retry budget.
  • Verification policies. None, AutomatedTests { command } (run right after a successful attempt, without a shell), IndependentAgent (a read-only reviewer item is spawned automatically), HumanApproval.
  • Budgets that can be measured. Wall time, item count, attempts per item, steps per attempt. No token or cost budgets, because the core cannot measure them honestly.
  • Graph integration through a port. A two-method gateway gives work agents recall and a provenance-carrying work_claim tool, without the work crate ever importing the graph crate.

Observability

  • Traces. --trace DIR writes the complete event stream of a run as NDJSON, including a context_snapshot from every agent at the end of its run, sub-agents and swarm members included.
  • The viewer. agentkit viz serves that trace to the browser, live while the run is going or afterwards from the file, through one code path. Tabs for agents, per-agent history and context, a timeline, a swarm sequence diagram with votes and dead letters, a force-layout graph view with provenance on every edge, and the work state.
  • Read-only and local. Binds only to 127.0.0.1, requires a random start-time token in the URL, has no writing endpoint, and does no secret redaction because a filter you trust is more dangerous than an honest warning.
  • Benchmark-scale. Point it at a results root and it finds every trace up to eight directory levels deep, with graph and work directories resolved per session.

Providers and platforms

  • Azure OpenAI, OpenAI, and anything OpenAI-compatible. Local models via Ollama, LM Studio, vLLM or llama.cpp work through the same path by pointing OPENAI_BASE_URL at the local server.
  • Demo mode without a key. A built-in, network-free model answers simple arithmetic so the binary is usable immediately after install and pipelines can be smoke-tested at zero cost.
  • Three-level configuration. Real environment variables beat a .env in the working directory, which beats ~/.agentkit/config.json. All three feed the same variables; placeholders count as unset.
  • Linux and Windows. Release binaries in a full and a CLI-only variant; a one-line PowerShell installer; cargo install for everything else; a static x86_64-musl build for containers.
  • Feature flags. openai, tui, pdf, ctxman, tiktoken, graph, work, viz. The default build of every library compiles with no HTTP or TLS at all.
Measured, not claimed. A bench binary measures pure framework overhead against the Python original with the same fake model on both sides: a geometric mean of about 3.6× faster, from 2.8× on the full loop to 5× on token counting and frontmatter parsing. With a real model the overhead disappears into network latency; what remains is compact memory, no GC pauses and predictable tail latency under many parallel helpers.
