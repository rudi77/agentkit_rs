Features

What you can do with agentkit

Begin with a model, a workspace and a task. This guide explains the capabilities you can add as the task grows, with examples of when each is useful. The getting-started guide provides the installation and configuration steps.

Run a task

The basic agent repeatedly asks a model what to do next, runs its requested tools and returns the results. For example, a model can search for a function, read its implementation and then explain it. Response text is streamed as it arrives.

The runtime limits the number of steps and retries failed model-stream setup with backoff. A cancellation flag lets the run and supported tools respond to a stop request. If the model requests several tools in one response, they can execute concurrently.

Conversation history can be saved between tasks. --continue reopens the most recent session, while --resume lets you resume a saved session. A session preserves the conversation; use the work runtime when you also need explicit task status and dependencies.

Read, edit and check code

With a real model configured, the executable supplies file, search and shell tools. A useful first task is to ask for an explanation of a known file. Then try a small edit with an explicit check, such as updating an error message and running its test.

OperationToolsWhat to expect
Find relevant fileslist_files, glob_files, grepDirectory listings, path matches or matching text.
Read contentread_file, read_pdfFile contents or extracted PDF text. PDF support requires its build feature.
Change fileswrite_file, edit_fileWrites within the configured workspace, with file checkpoints for undo.
Inspect Gitgit_status, git_diff, git_log, git_showRead-only repository information through structured arguments.
Run a check or programrun_shellA command subject to shell approval and configured rules.

File tools restrict writes to the workspace. --allow-read DIR adds a read-only root, for example a directory containing reference documents. Shell approval is a separate mechanism; it does not turn arbitrary commands into sandboxed file-tool operations.

In an interactive session, /undo restores the latest checkpointed file change and /undo all restores all tracked changes. This applies to edits made through the checkpointed tools, including shared helper edits. It does not reverse arbitrary shell effects.

--dry-run makes destructive tools report the intended operation without performing it. --verify prompts the model to check edited files before finishing. Project instructions come from AGENTS.md; optional frontmatter can also define shell allow and deny rules. Deny rules remain relevant when using -y to skip interactive approval.

Delegate to a helper

Use a sub-agent for a question with a clear return value: locate the parser, review a diff or report which tests cover a module. The parent calls task with a role and an assignment. The helper investigates in its own conversation and returns a result.

Built-in roles are general, explorer, reviewer and tester. Custom Markdown roles specify prompts, tool subsets and strategies. Helpers do not receive the task tool, so they cannot start another level of helpers through it.

Several requested tasks can run concurrently. All agents share the workspace; read-only roles suit independent investigations. Delegation can keep a large file investigation out of the parent's context, but it adds model calls and may omit details from the returned summary. The coding prompt encourages delegation and can remind the parent after repeated direct file reads.

Choose a strategy

react, plan and plain change the model's prompt preamble. They use the same tool loop. Choose plan_execute when you want an explicit planning phase followed by bounded runs for individual steps, with reflection and replanning available.

agentkit --strategy plan_execute "Review the configuration loader and propose tests for missing cases."

A planning strategy can organize a multi-step task, but a plan alone does not validate the result. State the evidence you expect, such as file references or a test command.

Load instructions and external tools

Skills provide task instructions

A skill is a directory containing a SKILL.md file and optional supporting material. agentkit first lists skill names and descriptions. The model loads the body when it needs the instructions, avoiding the cost of putting every skill into every prompt.

For example, a repository could provide a review checklist as a skill and load it only for review tasks. The loader supports Claude Code skill conventions, including directory and argument placeholders and tool-name mappings. Point --skills DIR at your collection.

MCP provides tools from external programs

MCP servers expose operations that appear alongside local tools. Configure servers in .mcp.json, then use --mcp NAME to restrict active servers or --no-mcp to disable them. A per-server tools list limits the exposed tools and their contribution to prompt size.

The client uses synchronous standard-input/output sessions. Server and tool selections can change during an interactive session through /mcp or the TUI's F2 panel. Only configure servers you intend to start: MCP startup is separate from approval of run_shell commands.

Use sessions and pipelines

agentkit "task" runs one task. --repl opens a line-oriented conversation with history and completion. --tui opens a terminal interface with progress panels, approval dialogs and queued input. The latter requires a build with TUI support.

In scripts, piped input becomes context and standard output contains the final result. -p suppresses progress output, while --format json requests JSON output and validates it with bounded retries. A JSON format check does not verify the meaning of the fields.

# Bash; report.txt must already exist
cat report.txt | agentkit -p "Summarize the findings in three sentences."

A JSON profile passed with --profile FILE can group a prompt, strategy, tool selection and other settings for a pipeline stage. See the user manual for profile fields and interactive commands.

2Model API or network failure

Shell completions are available for Bash, Zsh, Fish and PowerShell. --notify rings the terminal bell after a run, --model selects a model and agentkit read-pdf extracts PDF text without asking a model.

Manage a growing conversation

If an agent reads many files, the next model request may contain more material than is useful or allowed. --ctx DIR enables ctxman to manage that material and save the main agent's context state.

The default policy has two thresholds. At 60% of the configured budget, minor collection can move large tool results into a content-addressed store, which identifies saved content by a hash. At 80%, major collection can use model-backed compaction, with fact promotion before summarization. These are policy settings, not fixed limits for every model.

Externalized results remain available through expand_context_ref. Summarized conversation content may lose detail, so these two operations offer different forms of retention. The policy also distinguishes content kinds: tool results have a default lifetime of 12 turns, refetchable skills can expire and costly sub-agent results can be pinned.

Saved snapshots support resuming the main context. Helpers use temporary managed contexts with their own state. Deterministic rendering avoids changes to an unchanged prompt and can help provider caching. The tiktoken feature uses supported tokenizers for counting; that count need not match an unrelated model's tokenizer. --ctx-compaction-model selects a separate model for summarization.

Coordinate a discussion

A swarm is useful when participants need to respond to each other over several rounds. For example, a designer can propose an interface, a developer can describe implementation constraints and a tester can identify missing cases.

Each member owns a conversation and a mailbox. Tools let it discover peers, send or reply to messages, broadcast, propose a result and vote. The allowed connections form the swarm's topology: a mesh, chain, star or custom arrangement.

The dynamic swarm tool lets the main agent describe members and the completion policy. The current default limits allow up to 6 members and cap deliveries at 2,000. The default delivery budget is 120 per member; a broadcast consumes a delivery for each recipient. There is a 300-second idle limit and no default total-runtime limit, although a swarm specification can set one. These settings live in SwarmLimits. A full peer mailbox produces a reported dead letter.

A quorum is the required number of votes for a proposal. Reaching it establishes agreement under the configured rule; it does not replace checking the proposal. For runnable offline examples and comparisons with sub-agents, see the swarm examples.

Save project findings

A later task often needs a finding rather than the whole conversation that discovered it. The knowledge graph stores entities, claims, supporting sources and episodes of activity. Enable it with --graph DIR; add --graph-readonly when the task should only retrieve knowledge.

For example, the agent could record that a configuration loader reads a particular file format, with a source pointing to the implementation. graph_search, graph_neighbors and graph_evidence retrieve relevant information. graph_remember records working claims, while graph_promote applies the promotion checks for durable knowledge.

Working and canonical layers distinguish provisional material from accepted knowledge. Scopes control visibility, and the runtime supplies author and access information to tools. Claims retain provenance, meaning the record of where they came from. Canonical contradictions can supersede an older claim without erasing its history.

The store uses Markdown documents with structured frontmatter in an Open Knowledge Format bundle. Recall selects a small amount of relevant material for a task, including dynamically created swarm members. The graph is loaded into memory and rebuilds its index on writes; see the graph README before using it as a large knowledge store.

Resume a longer project

Use agentkit work when a project has dependent tasks and you need saved progress. A work item describes a task and its acceptance criteria. An attempt records one execution, and an artifact is an output file that later work can use.

The synchronous worker processes eligible items and creates a fresh agent for each attempt. A journal records state transitions, while leases and a writer lock track active ownership. After an interruption, resume recovers from the recorded state. Files or external effects left by an interrupted command still need to be taken into account.

Verification can be omitted or use an automated command, an independent read-only reviewer or human approval. Automated commands run after a successful attempt without a shell wrapper. Configure them for the workspace and dependencies the project actually has.

Budgets cover wall time, item count, attempts and steps. The work runtime does not enforce a monetary budget or a cumulative token budget. Optional integrations provide graph recall and claims, swarm execution, and Git isolation. The work guide documents their configuration and limitations.

Inspect a run

--trace DIR records events as newline-delimited JSON. agentkit viz --open opens a browser view with agent histories, context, a timeline and swarm traffic. With the relevant features and saved directories available, graph and work views show their state too.

The viewer reads traces during a run or afterwards. It can also discover traces under a benchmark results directory. Trace writing is supported in the CLI and REPL; the current TUI warns that --trace has no effect there.

The server listens on 127.0.0.1, checks a random startup token and offers read-only endpoints. Trace content is not redacted and may include files and tool output. Inspect it before sharing a trace with someone else.

Models and build options

agentkit connects to Azure OpenAI, OpenAI and compatible endpoints. A local server uses the same client path through OPENAI_BASE_URL. Tool use and structured output depend on what the chosen endpoint and model support.

The demo model is a scripted, network-free way to check installation and basic execution. It cannot analyze your project as a real model would. Configuration comes from environment variables, the working directory's .env and the user config, in that priority order.

Release binaries target Windows and Linux, with full and CLI variants. Cargo features select openai, tui, pdf, ctxman, tiktoken, graph, work and viz support. The app enables model connectivity and self-updating by default; several libraries have an offline default. The viewer has a local HTTP-server dependency.

The repository includes a framework microbenchmark using a fake model and a separate harness for agent benchmarks. A microbenchmark measures runtime overhead, while task completion with a real model also includes model latency, tool execution and answer quality. See how the project treats performance measurements.
