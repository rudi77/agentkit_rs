Following a task through the agent loop

Suppose you ask a coding assistant to fix a failing test. Before it can make a useful change, it needs to read the code. After the change, it needs to see what the test reports. Each result becomes input for the next decision. This repeated exchange is the part of an agent that agentkit runs.

We will first follow a smaller task: adding two numbers with a tool. It makes the interaction easy to inspect. Then we can use the same model of execution to understand file edits, events and the components that support longer tasks. You do not need to know the crate structure beforehand.

1. The model requests an operation

A language model receives messages and generates a response. When tools are available, that response can include a request to call one of them. The request names the tool and supplies its arguments. The application still has to execute it.

For our example, we register an add tool with two integer arguments, a and b. Its description and JSON schema tell the model what it accepts. The implementation is a Rust function that adds the values and returns the result as text.

Tool available to the model:
  add(a: integer, b: integer)

User message:
  What is 17 + 25?

Tool request returned by the model:
  name: add
  arguments: {"a": 17, "b": 25}

This is a simplified view of the request, rather than the provider's complete wire format. The important separation is between choosing an operation and performing it. The model supplies a request; the registered function determines what that request does.

2. The result goes back to the model

agentkit looks up add in its tool registry, passes in the arguments and receives 42. It then adds the tool result to the conversation and calls the model again. This second call lets the model use the result in its answer or request another operation.

The normal stopping condition is a model response without tool calls. A run can also stop because it reaches its step limit, encounters a failure or receives a cancellation request. Those conditions belong to the runtime around the model.

repeat, up to the step limit:
    ask the model using the current conversation
    collect its text and tool requests
    if there are no tool requests:
        return the final answer
    execute the requested tools
    add the requests and results to the conversation

This pseudocode leaves out retries, cancellation and optional verification so that the repeated exchange remains visible. In the source, Agent::drive and drive_inner implement the run and its surrounding bookkeeping.

3. A reproducible Rust example

We can test the exchange without a model server. FakeLlm returns a sequence of responses that we specify in advance: first a tool call, then a final sentence. The tool itself still executes. This makes the example useful for checking the framework's behavior, although it tells us nothing about a real model's ability to choose the right tool.

use std::sync::Arc;
use agentkit::{Agent, ToolRegistry};
use agentkit::llm::Chunk;
use agentkit::testing::FakeLlm;
use serde_json::json;

fn main() {
    let mut tools = ToolRegistry::new();
    tools.add(
        "add",
        "Adds two integers.",
        json!({
            "type": "object",
            "properties": {
                "a": {"type": "integer"},
                "b": {"type": "integer"}
            },
            "required": ["a", "b"]
        }),
        |args| {
            let a = args["a"].as_i64().ok_or("a must be an integer")?;
            let b = args["b"].as_i64().ok_or("b must be an integer")?;
            let sum = a.checked_add(b).ok_or("integer overflow")?;
            Ok(sum.to_string())
        },
    );
    let llm = Arc::new(FakeLlm::new(vec![
        vec![Chunk::tool(0, "c1", "add", r#"{"a":17,"b":25}"#)],
        vec![Chunk::text("The result is 42.")],
    ]));
    let mut agent = Agent::new(llm, tools);
    println!("{}", agent.run("What is 17 + 25?"));
}

The printed result is The result is 42. Both that sentence and the request were scripted; the addition was computed by the tool. The library setup instructions show the Cargo dependencies and where to save this code.

The request identifier c1 associates a tool call with its result. That association becomes especially useful when a model requests several tools in the same response. agentkit can execute them concurrently while keeping each result attached to its own request.

4. From addition to editing code

A coding task uses the same exchange with a different set of functions. Imagine a test that fails for an empty input. A possible sequence is:

  1. read_file returns the function and its tests.
  2. edit_file changes the empty-input branch.
  3. run_shell runs the relevant test command.
  4. The model reads the output and either revises the change or describes the result.

This sequence is illustrative. The actual requests depend on the model, the prompt and the tools it receives. The framework cannot infer that a patch is correct from the final sentence alone.

Tool execution also introduces permissions. File tools check paths against the workspace and any additional read roots. Shell commands use a separate approval mechanism because a command can do more than read or write a single checked path. Existing permission rules determine when a prompt is needed.

The optional --verify flag asks the model to check its work before finishing after file edits. It is a reminder within the conversation, not an independent proof of correctness. For a persistent project, the work runtime can apply a configured verification policy after an attempt.

Failure feedback is part of the exchange too. If the model names an unknown tool, the registry can return an ERROR: … result for it to read. A later request may correct the mistake. Retrying a model connection is a separate operation handled by the runtime; repeating a file edit is not automatically a safe substitute for reconnecting.

5. Observing a run

While the model and tools exchange messages, agentkit publishes events. A text_delta contains a piece of streamed text, a tool_call records a request and a tool_result records its outcome. Terminal renderers and the trace writer use these events to show what is happening.

Consider the addition example again. The terminal can display the call to add, while a trace file keeps the same event for later inspection. Neither needs to perform the addition itself. Each consumes information about a run.

An event also has a source. The main agent uses an empty source; helpers have labels. A helper finishing therefore does not imply that the main task has finished. This distinction matters once several agents contribute to the same visible run.

agentkit --trace .agentkit/trace "Read README.md and summarize the setup steps."
agentkit viz --open

Run the viewer in a second terminal to inspect activity while the first command is running, or open it afterwards. In the current implementation, the CLI and REPL support trace writing; the TUI does not. Trace files can contain the source text and tool output that the agent read.

6. What happens as context grows

Every file read can add more text to the next model request. After enough reads, the conversation may approach the model's context limit. Here, context means the messages and other material supplied to the model for its next response.

ctxman manages that material. One operation is externalization: saving a large tool result outside the prompt and retaining a shorter representation with a reference. If the agent needs the original content later, expand_context_ref retrieves it. This reduces the material in a request while retaining access to the saved result.

A different operation, compaction, summarizes conversation content when more space is needed. Summarization may omit details. Storing an original tool result and summarizing a discussion therefore have different consequences, even though both can reduce prompt size.

You enable managed context with --ctx DIR. For saved project findings, agentkit also offers a knowledge graph through --graph DIR. A graph claim might record that a particular module owns configuration loading, together with the file that supports the claim. A later task can retrieve that finding without replaying the full conversation that produced it.

7. Adding agents and persistent work

Once the single-agent loop is clear, the other execution modes become easier to place. Each addresses a different kind of coordination:

MechanismExampleWhat persists
Sub-agentAsk a reviewer to examine a diff and return findings.The parent receives the result; the helper has its own context during the task.
SwarmHave a developer and tester exchange proposals over several turns.Each member keeps its conversation while the swarm is running.
Work runtimeTrack dependent changes and resume after an interruption.Work items, attempts, artifacts and status are recorded on disk.

A swarm wraps each agent in an actor: a thread that owns the agent and processes messages from its mailbox. Members communicate through tools and can vote on proposals. The runtime counts those votes to decide whether the configured completion rule has been met. Agreement is an operational stopping condition; it does not establish that the proposal is correct.

The work runtime instead tracks progress across attempts. A completed item can leave an artifact, such as an analysis file, for a later item. After a process interruption, the journal tells the runtime which work was recorded as complete and which attempt needs recovery. This does not undo external effects of an interrupted command.

These components use the existing agent through tools and run interfaces. The core does not import the swarm, graph or work runtime. agentkit-app connects them in the executable. The crate map shows the dependencies, including the viewer's optional graph and work readers.

8. What to take away

In a tool-using agent, the model selects requests and the application executes them. Returning each result to the conversation lets a later response use information that was unavailable earlier. The same cycle supports a small arithmetic example and a coding task with several edits and checks.

For an initial task, focus on the model configuration, available tools and workspace. When the task grows, choose the component that addresses the difficulty you observe: managed context for prompt size, a graph for reusable findings, collaboration for separate contributions, or persistent work items for recovery and progress tracking.

Continue with your first run, the capability guide, or the implementation walkthrough. The tool registry and scripted model are useful next files to read alongside the loop.
