agentkit in five minutes: one loop, six crates, one rule

This is the map, not the territory. Every box below gets its own post eventually. For now: what's in agentkit, how the pieces fit, and the one rule that keeps it from turning into a hairball.

overviewloopcratesseams

The whole thing in four lines

while the model calls a tool:
    run tool -> append result -> ask model again
else:
    final answer

That's the agent. Honestly. Everything else is either a harness around that loop (retries, budgets, cancellation, parallel tool calls) or a crate that plugs into it from the outside. The loop is one function, Agent::drive, and it's been the same shape since day one.

How you talk to it: events

The loop doesn't print, render or log. It just publishes typed events: step, text_delta, tool_call, tool_result, final, done, a few more. The CLI listens. The TUI listens. The trace file listens. Sub-agents and swarm members push their events onto the same bus, tagged with a source, so one stream can carry a whole tree of agents and you can still tell the trunk from the branches.

Practical upshot: nobody has ever added a frontend by editing the loop. Not once.

The crates, in one breath each

  • agentkit — the loop, tools, skills, sub-agent roles, MCP, and the brains behind CLI, REPL and TUI. The core.
  • ctxman — context management as if it were memory management. A garbage collector with watermarks, a blob store for big tool results, a page-fault tool to pull them back. Byte-stable rendering so prompt caches stay warm.
  • agentkit-swarm — agents as actors. One thread, one mailbox, one agent. Peers talk through tools, finish by vote. Also: a swarm tool so an agent can spin up its own swarm mid-task.
  • agentkit-graph — a memory that survives the session. Entities and claims with provenance, stored as plain Markdown files. No database.
  • agentkit-work — for jobs longer than one run. Work items, dependencies, leases, retries, an append-only journal. The agent can die; the work state doesn't.
  • agentkit-viz — a read-only browser view of a run's trace. Agents, timeline, context, swarm traffic, graph, work. Localhost only.
  • agentkit-app — the actual agentkit binary. Pure wiring. The only crate that knows everyone.

The one rule

Dependencies point inward. The core knows nobody. Nobody knows their siblings.

Swarm, graph and work all depend on agentkit; agentkit has never heard of them. They don't import each other either — when work needs the graph, it declares a two-method port and the app fills it in. And viz doesn't link any of them: it reads a file. That's why the graph could swap its whole storage format and nothing else in the repo blinked.

How do the outer crates get in at all? Through exactly one seam: a closure that registers extra tools while the coding agent is being built. It was added for the swarm tool. Graph and work reuse it unchanged. Still the only extension point, and we'd like to keep it that way.

Three things you'll notice everywhere

  • No async. No tokio anywhere. HTTP is blocking, MCP is a mutex around a stdio pipe, parallelism is scoped threads. You can step through it, and it links into a static musl binary that runs in any container.
  • Identity comes from the runtime. A swarm member can't fake its sender. A graph writer can't pick its scope. A work attempt can't claim another item. None of those tools even have the argument.
  • Offline by default. Every crate builds with zero HTTP or TLS. No test touches the network — the loop is driven by a scripted fake model, the context manager is pinned by golden fixtures.

What's next

Each of those boxes deserves its own post: why ctxman treats context like RAM, why a swarm ends on a vote and not on a feeling, why the graph is Markdown, why work keeps a journal instead of a database.
