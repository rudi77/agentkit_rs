The Anatomy of agentkit: How One Loop Grew Into Six Crates Without Changing

agentkit started as a port of a teaching framework whose entire thesis fits in one sentence. Many releases and six crates later, that sentence is still the whole core. This post walks from the innermost function outward and explains, at each layer, what was added, what was deliberately not added, and what kept the centre from moving.

Start with the sentence

An agent is an LLM in a loop with tools. Everything else in agentkit is commentary on that sentence, and the code is organised so you can verify the claim by reading one function.

while the model calls a tool:
    run tool -> append result -> ask model again
else:
    final answer

The original is Python, part of a course on how agents work under the hood. The Rust port keeps the module names, the event type strings, the tool names and the behaviour one-to-one, on purpose. That decision looks like a constraint and turned out to be an asset: every later crate could be built on the assumption that the core would not shift under it, because the core was pinned to something external. When a deviation was necessary, it was made deliberately and written down in a "deliberate differences" list. The port is not a snapshot; it is a discipline.

The harness is where the engineering is

The loop itself is a dozen lines. Agent::drive is longer, because a loop that survives contact with real providers, real shells and real users needs a harness around it. Reading the harness tells you what actually goes wrong in practice.

  • Streaming with retries. Setting up the model stream is retried three times with exponential backoff, and the stop flag is honoured while waiting. When a provider sends Retry-After, that value wins, capped at sixty seconds. This was not a design nicety: before it, a rate limit from Azure named thirty seconds and the backoff burned all three attempts inside the same window, ending the run with "no answer". In a swarm, where N members share one deployment quota, the failure compounded.
  • Parallel tool calls. When a response contains several calls, they run on scoped threads and each keeps its own result. Cancellation reaches inside: a running shell command is killed, and calls that had not started return a soft "cancelled" so every call id still gets a result and the transcript stays well-formed.
  • Two kinds of error. An unknown tool or a malformed argument returns Ok("ERROR: …"). The model reads it and corrects itself; no error event is emitted. A tool that actually fails returns Err and emits one. This distinction is a contract — the frontends, the swarm and the work runtime all rely on it — and it is the reason timeout messages name their remedy. An error the model cannot act on is not an error, it is a loop it will retry.
  • Budgets and compaction. A step budget bounds every run; a token budget triggers summarising compaction of the message list when no context manager is attached. Two nudges, one for verification and one for delegation, are injected as user messages exactly once when a measured failure pattern appears: "done" without a check, or an orchestrator reading four files itself instead of asking an explorer.

None of these are in the pseudocode. All of them are in the function, as named steps, and each one traces to an observed failure rather than a hypothetical one.

The loop talks; everyone else listens

The Python original exposes the run as a generator: a frontend iterates over events. In Rust the port inverts that into a sink, FnMut(AgentEvent), and builds the convenience entry points on top: return only the final string, call back per event, or publish onto a bus. The events are typed — step, text_delta, tool_call, tool_result, plan, final, error, cancelled, done — with the same strings as the original and a Rust enum where Python had Any.

The event that carries the architecture is not in that list. It is the source field on every event. The orchestrator's own events have an empty source; a sub-agent's events are tagged with its role, a swarm member's with its id, a work attempt's with item and attempt number. One bus can carry a whole tree of agents, and any consumer can tell the trunk from the branches by one string comparison.

That field became a contract without anyone planning it. Frontends stop on the first empty-source done. Exit code 2 — API failure — counts only orchestrator failures, because the day a single 429 in one of three swarm members turned a completed, consensus-approved run into an empty stdout, it was obvious that a helper's transient failure must not veto the orchestrator's result. The plan-execute driver tags each phase as a source and emits the single root final/done itself, so a frontend does not need to know the driver exists.

The consequence for the codebase is simple to state: adding a frontend never touches agent.rs. The CLI renderer, the TUI, sub-agent forwarding, the NDJSON trace writer and the swarm's mirror are all subscribers.

A clone, a handle, and a rule

A tool is a JSON schema and a function from a JSON value to a string. The registry that holds them is cloneable because the function is an Arc, and cheap cloning is what makes two other things possible: parallel execution across threads, and sub-agents that own their own copy of the toolbox.

Cloning has a consequence that shaped a real piece of the API. The registry is copied when the agent is built. A tool that needs the live event bus and cancel flag — the task tool, later the swarm tool — cannot capture them at registration time, because they do not exist yet and will be different for every run. So such a tool holds a RunHandle: a shared cell that the loop overwrites at the start of every run. The rule that follows is small and has to be followed exactly — register before building, and pass the same handle to the builder — and the coding-agent builder shows the canonical wiring so nobody has to rediscover it.

There is a more general lesson in this. Where the Python original could reach for a closure over mutable state, the Rust port had to make the dependency explicit, and the explicit form turned out to be the one every later extension needed. The swarm tool blocks inside the orchestrator's tool thread and must see the user's stop key; it reads it through the same handle.

One level deep

A sub-agent in agentkit is not a type. It is an ordinary agent, built from a role — a system prompt, a tool subset, a strategy — and run inside a tool call. Roles are data: four built in (general, explorer, reviewer, tester) and any number loaded from Markdown files in the format Claude Code uses, so an entire development team can be assembled without writing framework code.

Two limits are enforced by construction rather than by checking. Sub-agents never receive the task tool, so delegation is exactly one level deep and recursion is impossible rather than forbidden. And all agents share a single workspace, which is why read-only roles exist and why the reviewer and explorer are built from the read-only subset of tools. When the swarm arrived, it inherited both limits unchanged: a member's registry is built from scratch and contains neither swarm nor task, and members default to read-only tools because a model-invented agent should get write access only when explicitly asked for.

Two kinds of strategy, kept apart

"Strategy" is a word that invites a trait hierarchy. In the original, ReAct, Plan and Plain are nothing but a system-prompt preamble, and the port keeps it that way — no separate execution paths, no dispatch. It is the example the coding guidelines cite for restraint: something you could abstract, and should not.

The port does add one real strategy, and it is instructive how. plan_execute is a driver around the loop, not a change inside it. It runs a planning phase, then one bounded ReAct pass per step, optionally a short reflection with bounded rework, and bounded replanning that swaps out the remaining steps when the plan proves wrong. The driver never touches Agent::drive; from the outside it is a sequence of source-tagged runs closed by one root done. It is listed as a deliberate deviation. Benchmarks later showed, quite separately, that the plain plan preamble was the single most valuable switch nobody had flipped in eight runs — a reminder that the cheap layer earns its keep before the expensive one is needed.

MCP without an event loop

The Model Context Protocol over stdio is line-delimited JSON-RPC. The Python client runs an asyncio loop in a thread to talk to it. The Rust port needs a mutex around a session and nothing else, and the whole repository is synchronous as a result: no tokio, no async traits, no runtime to configure. This is not a stylistic preference. It is what makes a static musl binary that runs in any benchmark container, and it is what lets the swarm model an agent as one thread owning one mutable reference.

The interesting engineering in the MCP module is not the transport but the toggling. Servers can be switched on and off live, and individual tools within a server too, without tearing anything down. The trick is to keep an MCP-free base registry: applying the hub returns it, and rewiring rebuilds the agent's tools from a clone of the base plus whatever is currently enabled. Only an atomic flag flips per server; sessions live on. A user-wide configuration is merged underneath the project one, and because a server is a process launched at startup with no approval gate, a name collision that changes the command is surfaced as a warning rather than letting a repository-local file quietly take over a name the user trusts.

The frontend that is a filter

The executable has three faces — one-shot, REPL, TUI — and a fourth that matters more for composition: it is a proper Unix filter. Standard input is context and is appended to the query; standard output, once piped or in print or JSON mode, carries only the cleaned final result; standard error carries everything else. Exit codes are a contract: 0, 1 runtime, 2 API, 3 context or prompt, 4 format not satisfiable. -- ends options, unknown options are reported, broken pipes end cleanly.

The architectural point is where this lives. The stream contract is hexagonal — the standard streams are adapters — and the agent core is untouched by it. The pipe primitives (exit codes, output format, stdin reading, JSON extraction, outcome classification) sit in one decoupled, tested module; argument parsing is in the binary; and everything the CLI and TUI share, from building the coding agent to rendering a plan, is in one shared module where the only injected difference is the approval callback: stdin in the CLI, a dialog in the TUI.

A pipeline of one agent per stage, each with its own --profile — system prompt, strategy, tools, skills, MCP allowlist — is the composition model the project recommends. The worked example is an accounts-payable pipeline that reads invoices, checks e-invoice conformance through a deterministic tool, extracts and validates with model-driven stages, and exports a bookkeeping batch: deterministic tools for facts, agents for judgement.

The one seam

Here is the part that makes the rest of the story possible. The core has exactly one extension point: a closure, extra_tools, that receives the registry and a context object — run handle, model, the shared coding tools, the MCP hub, skills, roles, the dry-run flag — while the coding agent is being built.

It exists for one reason, and the reason is written down. The swarm tool lives in a crate that depends on the core, so the core cannot know it. A data field would not have sufficed: the run handle, the approval callback and, in the TUI, the model itself only come into existence inside the build function, and two registries cannot be merged. The closure runs before the MCP hub is applied, so anything it registers becomes part of the MCP-free base and survives a live toggle. It is also where dry-run propagates: every registry a run creates, including every sub-agent's and every swarm member's, is blocked independently, because otherwise a helper would write what the orchestrator may not.

The graph and the work runtime reuse that seam without modification. That is the entire integration story of the outer crates: a closure registers tools, the tools carry a run handle, events flow back over the bus. Nothing else was needed, and nothing else was added.

Outward: context as memory

Naive compaction is lossy. At some point it throws away the thing you needed. ctxman is a port of a C# context-management service, reduced to its deterministic core and made synchronous, and its mental model is memory management rather than summarisation.

A static region — system prompt, tool definitions — is epoch-versioned and immutable within an epoch. A working set — messages, tool results, skill bodies — is managed by a garbage collector. At sixty percent of the budget a minor collection externalises large tool results losslessly into a content-addressed blob store, leaving a summary and a reference; the model pulls them back on demand through a page-fault tool. At eighty percent a major collection runs model-backed compaction, but promotes durable facts to long-term memory first, so the summary cannot lose them. The whole context, blob references included, is snapshotted after every run and a restart continues exactly where it stopped.

Two decisions define the crate. ctxman never calls the model itself: compaction and promotion run through host-implemented traits, which keeps it offline-testable and leaves the choice of model with the agent. And rendering is byte-stable: identical segment state produces identical provider bytes, which is what keeps prompt caches warm. That property is pinned by golden fixtures copied from the original, and the rule is absolute: they are never regenerated to make a test pass, because a byte diff there means behaviour changed.

Integrating it into agentkit taught two things worth recording. The spec's lifetime for tool results — two turns — came from a different domain; a coding agent reads a file and works on it for several turns, and when the content was gone it read the file again. A benchmark trace counted 280 repeat reads of the same file with a median distance of three turns. The lifetime is now twelve, and because tool results externalise rather than vanish, the context does not get more expensive. And the growth that matters happens in the helpers: in one measured run three sub-agents read sixty-one files while the orchestrator read three. Helpers now get an ephemeral managed context — garbage collection and externalisation, no snapshot — because a snapshot for something that never resumes is pure write load, and a shared state directory across parallel helpers would be a correctness bug.

Outward: agents as actors

The swarm crate has one principle, stated in its first paragraph: a swarm agent is a normal agent owned exclusively by an actor. The actor adds a mailbox, an identity and peer communication without changing the loop. One actor is one OS thread and one &mut Agent, so exactly one message is processed at a time. There are no mutexes around agents, no nested runs, and each agent's history is deterministic. The guidelines forbid concurrency in reserve; here the thread is the non-reentrancy argument, and that is the concrete need.

AgentActor "architect"      AgentActor "developer"      AgentActor "tester"

├── Mailbox (bounded)       ├── Mailbox                 ├── Mailbox
└── permitted peers ────────┴──── swarm_send / reply ───┘
                                   │
                      swarm_propose / swarm_vote
                                   ▼
                          CompletionActor (counts votes, no LLM)

The agent sees the swarm through six tools, and the design shows up in what the tools do not take. There is no from argument; the sender is set by the closure, so no member can impersonate another. Topology is a capability: a member that was not handed a reference to a peer cannot send to it, which is stronger than any check. Every send is non-blocking, a full mailbox produces a dead letter, and shutdown reaches every actor through a receive timeout even when its mailbox is full. Deadlock-freedom is a property of the construction, not of careful use.

Completion is deterministic and never semantic. A quorum of votes ends the swarm — but not immediately: a voting window collects the remaining votes so the best-supported proposal wins, not the first one past the post. A rejection goes back to the proposer with its critique, because a vote otherwise goes only to the counter, and a rule saying "incorporate the objections" would be an instruction to do the impossible. An exhausted message budget brakes rather than kills: sends stop, work in flight finishes, and consensus can still close the run through the budget-free proposal and vote paths. Each of these came from a real run where the naive version lost the work the budget had just paid for.

The dynamic variant is the swarm tool: the orchestrating agent describes members, prompts, tool access, topology and quorum as JSON and blocks until the result — including the full vote, so a run is explainable afterwards — comes back. Swarm traffic is mirrored onto existing event types with the member as source, because a new event type is a behavioural contract that every frontend would have to learn, and a tool result already carries the same information.

Outward: knowledge with provenance

The graph crate draws a line the other crates respect: the graph stores knowledge, peer messages request actions, and what reaches the model's context is decided by recall, never by the graph. The model is entities, claims (subject, predicate, object, with status, confidence and sources), sources and episodes, on two orthogonal axes — a layer, working or canonical, that says how reliable something is, and a scope that says who owns it. Visibility runs exclusively through scope; what is not in your view does not exist for you, not even as an error message.

The concurrency story is small and exact. Readers take a lock only long enough to clone an Arc and then traverse an immutable snapshot with no locks at all. Writers commit synchronously: disk first, then the swap. A receipt means the change is visible to everyone, so read-your-writes needs no queue, no writer actor, no revision timeout — all of which the product requirements had sketched and all of which were deleted because a local commit takes microseconds. The revision number is a store-wide monotonic counter that serves as mutation id, audit mark and recency signal at once, and unlike a timestamp it is deterministic.

Two invariants are structural. A model cannot canonicalise its own claims: the remember tool accepts only observations and hypotheses, and only promotion — with at least one source — sets confirmed. And no tool has a scope, agent or author argument; those live in an access object captured at registration. The same principle as the swarm's from, applied to memory.

On disk the graph is an Open Knowledge Format bundle: one Markdown document per entity with YAML frontmatter, layer and scope in the directory path, everything graph-specific under a single extension key so any OKF consumer sees exactly one unknown field. The frontmatter is the truth and the body is decoration, which means a human can edit the prose without endangering a rebuild. There is no SQLite, because the bundled build drags a C compiler into a pure-Rust repository and into the static benchmark binary; there is a minimal hand-written YAML adapter instead, deliberately narrow, where an unknown construct is a hard error rather than a silent swallow.

Outward: the state must live for hours

The work runtime starts from a reframing. It is not the agent that needs to live for hours; it is the work state. Agents and swarms may be short-lived. The runtime makes no domain decisions and solves no tasks; it knows which task is open, who is working on it, what it produced and where to resume after a crash.

A project is decomposed into items with dependencies, acceptance criteria and a verification policy. A synchronous single-worker loop takes ready items in dependency order and builds a fresh agent per attempt through the ordinary coding-agent builder, registering three tools through the same seam as everyone else: add an item, store an artifact, submit the attempt with each acceptance criterion rated individually. Run, item, attempt and agent ids have no tool argument. The identity is the runtime's; this is enforced structurally, not validated.

Storage is an in-memory state behind a read-write lock plus an append-only JSONL journal. The important decision is that a checkpoint is an appended snapshot line, not a rewrite. An earlier draft rewrote the whole journal at every checkpoint and thereby destroyed the very timeline the events command was supposed to show; now history stays intact, and reopening replays only what came after the last snapshot. Ready and Blocked are derived views rather than stored states, so they cannot drift from the dependency graph when a predecessor is reset. Recovery completes half-written transitions instead of discarding them, so a crash between "attempt finished" and "item completed" does not re-run the item. An interrupted attempt does not count against the retry budget, because a killed process is not a failed attempt. And a lock file — created atomically, removed on drop, never auto-cleaned by guessing whether a PID is alive — keeps a second worker from corrupting the journal.

Verification is a property of the item. None, for the common case. An automated command, run right after a successful attempt without a shell. An independent agent, which spawns a read-only reviewer item automatically — itself unverified, because a reviewer that needed reviewing would regress forever. Or human approval. The graph is reached through a two-method port defined in the work crate and implemented in the executable, so the work runtime never imports the graph and the one-way rule holds.

Outward: the trace is the seam

The viewer is the one crate that consumes nothing from the agent side. It reads the NDJSON trace a run writes with --trace, defines its own mirror types with owned strings, and keeps an unknown event variant with its raw form instead of dropping it — because a viewer that fails on a new event type is useless precisely when you need it. Inside it is hexagonal: the projections know neither HTTP nor the filesystem and are tested without a server.

Everything about it is shaped by what a trace contains: every file the agent read, every shell output, every model reply, and in a repository with a .env possibly secrets in plain text. So the server binds only to loopback with no option to change that, checks a random start-time token before it touches the filesystem, has no writing endpoint, and does no secret redaction, on the argument that a filter you trust is more dangerous than an honest warning. It polls instead of streaming, a documented deviation from its own plan, because server-sent events in a tiny synchronous HTTP library would have meant a thread per connection and a hand-written HTTP frame for a difference that is invisible on localhost. The sequence diagram and the force-directed graph layout are hand-written SVG and a hand-written simulation, with a circular start layout so the same input draws the same picture, and no vendored JavaScript.

The crate that only wires

There is a reason the executable is its own crate. The swarm depends on the core; the executable needs both; a binary inside the core would be a Cargo package cycle. So the app is thin wiring with no domain logic: it parses arguments, renders the event stream, injects the swarm and graph tools through the seam, hands the work CLI a model builder and an approval callback, adapts the graph to the work runtime's port, and dispatches the viewer. It is the only crate that knows all of them, and therefore the only place such adaptation may live.

It also carries one deviation that shows how far a single decision can reach. The core's release profile aborts on panic to save a megabyte. The app keeps unwinding, because the swarm supervisor detects an actor panic through a failed thread join and shuts the swarm down in a controlled way; with abort, the whole process would die.

What held the centre

Six crates, one seam, and a core that did not move. Looking back, four things did the holding.

Dependencies point one way. The core does not know its siblings; the siblings do not know each other; where one needs another, it declares a port and the app implements it. The viewer reads a file. This is not merely tidy: it is why a change in the swarm cannot break a benchmark run, and why the graph could switch its storage format without any other crate noticing.

Identity comes from the runtime. The swarm's from, the graph's author and scope, the work runtime's run and attempt, the claim tool's provenance — none has a tool argument. A model cannot impersonate, cannot write into a foreign scope, cannot confirm its own hypothesis. No validation has to be right for that to hold.

Limits are structural. One level of delegation, no recursion in swarms, topology as capability, file names from a whitelist, an empty sandbox root rejected at construction. Each is a shape of the code rather than a check inside it.

Decisions are measured and written down. The tool-result lifetime, the delegation prompt, the plan strategy, the voting window, the journal checkpoint: each traces to a counted failure in a real run, and each is recorded in a "deliberate decisions" section next to the code. The guidelines say the boring solution wins. What they do not say, and what the repository shows, is that the boring solution is easier to defend later, because you can still say why.

That is the anatomy. If you want to see it move, the get-started page takes you from install to a swarm in a few commands; if you want the map without the narrative, the architecture overview is the same material as a reference.
