The harness around the model: its parts and what they change in a run

Give the same model the same failing test twice, once through a bare loop and once through a coding assistant, and the two runs can end differently. One stops when the connection drops in step 40. The other waits, reconnects and continues. The model is identical in both; the program around it differs. That surrounding program is commonly called the harness.

This article describes the harness in agentkit: which parts it consists of, what each part does when something goes wrong, and what our benchmark runs say about the effect on reliability, cost and solved tasks. It assumes you know the basic exchange between a model and its tools. If you do not, Following a task through the agent loop introduces it with a small example.

1. What the harness is

A model produces text and tool requests. Everything else in a run is done by the program that calls it. In agentkit this program has seven jobs. It controls the loop. It supplies the instructions the model works under, including skills that are loaded on demand. It manages the context, which is the part of the conversation that goes into each request. It executes tool requests, and before that it decides whether a request is permitted. It checks a few conditions before it accepts an answer as final. And it reports what happened. We use harness for these jobs together.

The grouping helps with a practical question. When a run fails or costs more than expected, you want to know which part was responsible. A dropped connection is a loop-control matter. An answer that claims a change which does not exist in the working tree is a matter for the finishing checks. A request that has grown to hundreds of thousands of tokens is a context matter. A command that should never have run is a permission matter.

These parts influence four properties of a run, and it is useful to keep them apart:

PropertyQuestionHow it shows
ReliabilityDoes the run end in a defined state, and does it survive failures that have nothing to do with the task?Final answer, or a specific end marker and exit code.
EfficiencyHow many model calls, tokens and seconds does the run need?Steps, tool calls, wall-clock time.
Result qualityIs the task actually solved?Tests of a benchmark, or your own review.
ContainmentWhat can a mistaken or misled request change, and where?Refused calls, approval prompts, the state of your working tree.

A change in the harness often improves one of these and costs another. Several sections below show such a trade with measured numbers.

2. One step, seen from the harness

Take the task from the introduction: a test fails for an empty input, and the agent should fix it. The run consists of steps. In each step the harness sends the conversation to the model, reads the response, executes the requested tools and records their results. Figure 2 follows one step and notes what the harness checks at each point.

Most of these interventions have the same form: the harness turns a problem into a message that the model can read in the next step. A tool that does not exist produces an error text as its result. A missing verification produces a user message that asks for one. The model then decides what to do. This keeps the loop simple, and it means that such an intervention is a request to the model, without a guarantee that the model follows it. The exceptions are the hard limits: the step limit, the time limit of a shell command, and the rules about which paths and commands are permitted. These hold regardless of what the model answers.

3. A reproducible example: two mistakes, one answer

We can watch two of these interventions without a model server. The example extends the addition tool from the agent-loop article. FakeLlm returns responses that we specify in advance. Here it first requests a tool named ad, which does not exist, then requests add with arguments that break off in the middle, and then makes a valid call.

To run it, set up the project as described in the library section of the getting-started guide and use this as src/main.rs:

use std::sync::Arc;
use agentkit::events::{EventData, TOOL_RESULT};
use agentkit::llm::Chunk;
use agentkit::testing::FakeLlm;
use agentkit::{Agent, ToolRegistry};
use serde_json::json;

fn main() {
    let mut tools = ToolRegistry::new();
    tools.add(
        "add",
        "Adds two integers.",
        json!({
            "type": "object",
            "properties": {
                "a": {"type": "integer"},
                "b": {"type": "integer"}
            },
            "required": ["a", "b"]
        }),
        |args| {
            let a = args["a"].as_i64().ok_or("a must be an integer")?;
            let b = args["b"].as_i64().ok_or("b must be an integer")?;
            Ok((a + b).to_string())
        },
    );
    let llm = Arc::new(FakeLlm::new(vec![
        // 1: a tool name that does not exist
        vec![Chunk::tool(0, "c1", "ad", r#"{"a":17,"b":25}"#)],
        // 2: the right tool, but the arguments are not valid JSON
        vec![Chunk::tool(0, "c2", "add", r#"{"a":17,"b":"#)],
        // 3: a valid call
        vec![Chunk::tool(0, "c3", "add", r#"{"a":17,"b":25}"#)],
        vec![Chunk::text("The result is 42.")],
    ]));
    let mut agent = Agent::new(llm, tools);
    let answer = agent.run_with_events("What is 17 + 25?", None, |event| {
        if event.etype == TOOL_RESULT {
            if let EventData::ToolResult { name, result } = &event.data {
                println!("{name} -> {result}");
            }
        }
    });
    println!("{answer}");
}

Run against the source tree of 2026-11-21, it prints:

ad -> ERROR: unbekanntes Tool 'ad'
add -> ERROR: Die Argumente dieses Tool-Aufrufs sind kein gültiges JSON (EOF while parsing a value at line 1 column 12); er wurde NICHT ausgeführt. Wiederhole ihn mit gültigem JSON.
add -> 42
The result is 42.

The messages are German, like all texts the harness writes into a conversation in the current version. The first says that the tool ad is unknown. The second says that the arguments are not valid JSON, that the call was not executed, and that it should be repeated with valid JSON.

Neither mistake ended the run. Each produced a tool result, the conversation stayed complete, and the next model response could react to it. Because the responses are scripted, the example shows what the harness does with these two mistakes. Whether a real model corrects itself after such a message is a property of that model.

The second message exists for a reason found in practice. Earlier, broken arguments were silently replaced by an empty object. The tool then reported a missing required field, and the model looked for its error in the wrong place. The wording of what a harness sends back determines how many further steps the model needs.

4. Loop control: limits and recovery

Loop control decides whether there is a next step. The ordinary end is a model response without a tool request. The other ends are a reached step limit, a cancellation and a model call that failed for good. Each has its own end marker, and the executable maps them to exit codes (section 11).

The step limit bounds the cost of a run that makes no progress. The library's builder uses 12 steps unless told otherwise; the agentkit executable sets 600 and accepts --max-steps. A run that reaches the limit ends with the marker (max_steps erreicht) instead of an answer.

Recovery from model-call failures matters more as runs get longer. A run of several hundred model calls is likely to meet a rate limit or a short network failure at some point. Without recovery, that one failure discards everything the run has done. agentkit distinguishes three cases:

FailureWhat the harness doesReason
The connection cannot be established, or the provider answers with a rate limit (429), a timeout (408) or a server errorUp to three attempts. The wait starts at 500 ms and doubles. If the provider names a waiting time, that time is used, up to 60 seconds.These failures usually pass. A named waiting time above 60 seconds ends the attempts at once, since a shorter wait would fail again.
Another 4xx answer, for example an invalid key or an unknown modelNo further attempt.The next attempt would get the same answer; waiting only delays the error message.
The response stream breaks off in the middleThe step is repeated up to two times.No tool has run in this step yet, so the conversation is unchanged and repeating has no side effect. A refusal or content filter is not repeated.

One detail of the first case came from a measurement. Sub-agents and swarm members share one model deployment and therefore one quota. At first, each agent waited on its own after a rate limit. While one waited, the others kept sending requests and kept the limit active. In the observed runs, three sub-agents with independent retries all ended without an answer and lost what they had already read. The waiting time is now shared by all agents in the process: when one agent is told to wait 30 seconds, every agent waits before its next request. The comments in agent.rs record this and the other measurements quoted in this article.

Cancellation is cooperative: the harness checks a stop flag before each step, while reading the stream, before running tools and while waiting. Its contribution to reliability is less visible. If you stop a run after the model has requested three tools and before they have run, the conversation would contain requests without results, and the provider would reject every later request in that session. The harness therefore records a placeholder result for each pending call. The session stays usable after the interruption.

5. The tool layer: what the model gets back

The tool layer executes requests and returns text. This section covers what a result may cost in tokens and time. What a request is allowed to do is the subject of the next section.

A test run or a build can print megabytes. Sent back unchanged, that output would fill the next request and every request after it. The harness cuts each tool result to 16,000 characters. It keeps the beginning and the end and marks the gap, and the end receives two thirds of the space. In test and compiler output the decisive lines, such as the failure and the summary, stand at the end. An earlier version that kept only the beginning removed exactly those lines.

When the model requests several tools in one response, the harness runs them concurrently and keeps each result attached to its request. Four file reads then take about as long as the slowest one. This is an efficiency gain in wall-clock time; it does not change the number of tokens.

Shell commands get a time limit, 120 seconds in the executable unless you set --shell-timeout. On expiry or cancellation the harness ends the command's whole process tree, so a test runner's child processes do not keep running and holding locks.

The time limit also gave us a result worth reporting because it is negative. On Terminal-Bench, the benchmark setup used 60 seconds, which cut off compile tasks: the run over seven tasks recorded seven shell timeouts. With 600 seconds it recorded none. The number of solved tasks was 1 of 7 in both runs. The defect was real and its repair complete, and still it was not what kept the tasks from being solved. A harness fix that removes waste does not automatically raise the success rate.

6. Permissions: what a request may do

A model can request a wrong action for ordinary reasons: it misreads the task, or it confuses two directories. It can also be misled, because the files, web pages and tool results it reads are text, and text can contain instructions. The harness cannot prevent the request. It decides what happens to it. agentkit applies several rules before a tool acts, and each rule answers a different question.

QuestionRuleHow you set it
Which files may be read or written?File tools resolve every path and accept it only inside the workspace or a directory you added. A symbolic link that leads outside is refused. Writes below .git/ are refused, because git starts programs from there.-w, --add-dir, --allow-read for read-only directories, --protect-paths for files that must not change
Which shell commands may run?Each command goes to an approval callback: the terminal asks you, -y approves everything. Patterns under deny in the project instructions are checked first and also hold with -y.-y, deny and allow lists in AGENTS.md
What may run without asking?Hooks and MCP servers are programs that start without an approval prompt. Hooks are therefore read only from your user configuration, never from the repository. If a repository redefines an MCP server name you already use with a different command, agentkit prints a warning. An allow list from a repository takes effect only after you confirmed it once.user-level hooks.json, .mcp.json, --mcp, --no-mcp
What may a helper do?A sub-agent role receives a subset of the tools; the exploring and reviewing roles cannot write files. A sub-agent cannot delegate further.role definitions, --agents DIR
Can I see the plan without effects?With --dry-run, tools that change something report what they would do and do nothing. The tool descriptions stay the same, so the model behaves as in a real run. The rule also applies to sub-agents and swarm members.--dry-run

A refusal has the same form as the errors in section 3. The tool returns a text, in German, that says the user rejected the command or that the path lies outside the sandbox, and the run continues. The model can then choose another way, for example editing a source file after a write to a protected test file was refused. A refusal that ended the run would make every permission rule a reliability problem.

These rules have a stated limit, and the source says so in the same words: they slow down a model that errs, and they are not a security boundary against an attacker. The deny patterns compare text and do not resolve variables, quoting or command substitution. A pattern for git push stops that command and does not stop a command that assembles it from parts. The path check does not protect against a link that is swapped between the check and the access. An approved shell command runs with your user's rights and can reach anything you can. If the code or the task is untrusted, the isolation has to come from outside the harness, such as a container or a virtual machine. Our benchmark runs execute every task in a container for the same reason.

Permissions also cost something. Every approval prompt stops the run until you answer, and -y removes that cost together with the check. For unattended use, the combination that keeps most of both is a narrow workspace, deny patterns for the commands you never want, and -y inside an isolated environment. We have no measurement of how often the rules refuse a request in ordinary use.

7. Context management: what the model sees in each step

Each request contains the system prompt, the tool descriptions and the conversation so far. The conversation grows with every tool result, and a coding task consists mostly of tool results: file contents, search hits, test output. Three things follow. The request must stay below the model's limit, or the run ends. Every token in the request is paid for again in each following step, so a file read in step 5 of a 100-step run is sent about 95 more times. And whatever is removed to save space may be needed later.

In the executable, a component called ctxman manages this unless you turn it off with --no-ctx. It works with a token budget and three thresholds, each a fraction of that budget:

Context reachesOperationWhat is lost
60% of the budgetLarge tool results are saved outside the request. A short reference stays in their place, and the agent can fetch the original with the tool expand_context_ref.Nothing; the original is stored.
80%Older turns are summarized by a model call. Before that, durable facts are extracted and saved.Details that the summary omits.
95%Material is removed immediately while the request is assembled.The removed material.

The order matters for both cost and quality. The first operation is free of model calls and loses nothing, so it runs first. The lossy one runs only when the first was not enough. Watching an agent's context grow and shrink follows the three thresholds through a recorded run, with the viewer's charts.

A second setting decides how long a tool result stays in the request at all. The policy ctxman was specified with removes a tool result after two turns. For a coding agent that was too short: it reads a file, works on it for a few turns, the content is gone, and it reads the file again. In a SWE-bench run we counted 280 repeated read_file calls on a file the same agent had already read, 56% of them after the content had expired. One exploring sub-agent read the same four files four times each, and 567 of the 649 KiB in its context were duplicates. agentkit now keeps tool results for twelve turns. Large results still move out of the request at the first threshold, so the longer lifetime does not keep them in every request.

Context management also affects reliability. A helper with a small budget can reach a state in which its system prompt and tool descriptions nearly fill the budget, and the cleanup has nothing left to free. Earlier this ended the run without an answer. The budget is a limit we set ourselves, below the model's own, so the harness now sends that one step with the unreduced conversation and continues. The context state is also saved after every run, including cancelled and failed ones, and a resumed session continues from it.

When the library runs without ctxman, a simpler mechanism summarizes older messages once an estimated token budget is exceeded. It keeps the last four messages and the wording of the current task. Summarizing costs a model call, so the mechanism itself can become the expense. In one measured case the four kept messages alone exceeded the budget of 8,000 tokens, because each tool result had 16,000 characters. The harness then summarized in almost every step: seven summary calls in nine steps, each mostly re-summarizing the previous summary. Since then it waits for eight new messages after an attempt before it tries again. The same scenario needs two summary calls.

Two fixed parts of the request are not conversation and cannot be summarized: the system prompt and the tool descriptions. An MCP server with dozens of tools adds their descriptions to every request. A tools list per server in .mcp.json limits which ones are sent.

A related decision concerns where additional text is placed. Before each user turn, the executable can add findings recalled from the knowledge graph. The harness puts them in front of the user message and leaves the system prompt untouched. The beginning of every request therefore stays identical across a session, which is the condition under which providers can reuse a cached prompt prefix. We have not measured the resulting saving, so take this as the intent of the design.

8. Instructions and skills: what the model is told

The model's behavior in a run depends on text it receives before the task: the system prompt, a paragraph that sets the working strategy, and the project instructions from a file such as AGENTS.md. All of it is part of every request. That creates a conflict. The more procedures you describe, the more the model knows how you want things done, and the more tokens every step costs, including the steps in which none of those procedures apply.

Skills resolve this conflict for instructions that are needed only sometimes. A skill is a directory with a file SKILL.md. The file starts with a name and a one-line description and continues with the instructions themselves: a review checklist, the steps of a release, the conventions for a migration. agentkit gives the model two tools. list_skills returns the names and descriptions. read_skill returns the full text of one skill. The system prompt only carries a short paragraph that asks the model to look at the list first.

skills/
  review-checklist/
    SKILL.md        name, description, then the instructions
  release/
    SKILL.md
    notes-template.md

agentkit --skills skills "Review the staged change."

The directory layout is schematic. In this example the model would call list_skills, see the two descriptions, load review-checklist and work through it. The text of release never enters the conversation. Twenty skills cost twenty lines in one tool result, and a full text is paid for only in the runs that load it. The loader accepts the conventions of Claude Code skills, including placeholders for the skill's directory and for arguments.

For the properties from section 1, this means lower cost per step than putting the same texts into the system prompt, and a consistent procedure for recurring tasks, since the steps come from a file and not from the model's recollection. Both statements describe the construction. We have not benchmarked runs with and without skills. The mechanism also depends on the model: it has to call the list, pick the right entry and follow the text. A description that does not say when the skill applies will not be picked.

One observation about instructions in general comes from a recorded run. The coding prompt once contained two paragraphs: an older one that told the agent to get an overview with the file tools first, and a newer one further down that told it to delegate exploration to a sub-agent. The model followed the earlier, more concrete paragraph, read four files itself in one step and ignored the later one. Adding a sentence that the second paragraph takes precedence did not help. The contradiction had to be removed, and the prompt is now assembled differently depending on whether a task tool exists. Where an instruction matters and a model may still ignore it, agentkit adds a check in the loop. Those checks are the subject of the next section.

9. Checks before a run may finish

The most consequential stage for result quality is the moment the model answers without a tool request. Normally that answer is final. In a few situations the harness instead adds a user message and continues the loop. agentkit's source calls such a message a nudge.

SituationMessage to the modelHow often per run
The answer was cut off at the model's output limitGive the answer again, shorter.Once
Files were changed and no test command has succeeded since (only with --verify)Write a check that shows the described failure, see it fail without the change and pass with it, then run the existing tests.Up to three times
The run wants to finish without having changed any file (only with --verify)Either state that nothing was changed, or make the change now.Once
The main agent has read four or more files itself and has a task toolHand the remaining exploration to a sub-agent.Once
The same call with the same arguments returned the same result three timesA repetition yields nothing new; change the approach.Once

The last two are sent after tool results, during the run. They address cost: file contents that stay in the main conversation for the rest of the task, and steps spent on a call whose result is already known.

The verification check has the longest history, and it shows how a harness rule is tuned in both directions. Its first version treated any successful shell command as a verification. In benchmark runs a plain ls satisfied it, and runs ended with a detailed success report and an empty diff. The rule was tightened: only a recognized test command counts, and delegating to a sub-agent raises it again because the main agent cannot see whether the helper changed files. On the same 17 tasks, the average rose from 20.7 to 37.6 steps and from 95 to 195 seconds per task. One Terminal-Bench task that had been given up after 17 steps with the claim that make was unavailable was now solved. The agent gave up less often and each task cost roughly twice as much.

A measurement on 2026-11-21 showed the opposite failure. The system prompt asks for a review by a read-only sub-agent before finishing. Under the rule above, that review raised the obligation again each time. Of 64 Aider Polyglot tasks, 16 received all three messages and repeated their verification four times; one task was solved after 8 steps and then ran for 35 more. In 22 of the 24 runs in which finishing had been refused, a tester sub-agent had already run the tests after the last change. The rule in the development branch at the time of writing is narrower: only delegation to a role that can write files raises the obligation, and a successful test run by a sub-agent satisfies it. This change is not part of 0.33.0-rc.4.

Both corrections came from reading recorded runs. A check that is too weak lets wrong answers through; one that is too strict spends steps on work that is already done. Neither shows in a unit test of the rule itself.

10. Prompt strategy and delegation

For two harness settings we have benchmark numbers: the strategy paragraph at the start of the system prompt, and whether the model may hand subtasks to sub-agents.

The numbers in this section come from the benchmark report (in German) for agentkit 0.21.0, measured in August 2026 with one small model, an Azure OpenAI deployment of gpt-5.4-mini. The tasks were 64 from Aider Polyglot and 25 from SWE-bench Lite, with a step limit of 100. They compare configurations of agentkit with each other. They say nothing about other models and cannot be compared with public leaderboards.

The strategy flag -s plan changes one paragraph of the system prompt: the model is asked to write a short numbered plan first and then work through it. The loop is the same.

ConfigurationPolyglot (64)SWE-bench Lite (25)Together
Default prompt, round 354458 of 89
-s plan, round 357865 of 89
-s plan, round 4 (another day, another build)59867 of 89

On SWE-bench Lite, the number of runs that broke previously passing tests fell from 6 to 3 in round 3. With 25 instances, the step from 4 to 8 solved tasks is not statistically secured: the same configuration solved 4 of 10 and 1 of 10 of the same instances in two runs that week. What supports the result is that the plan prompt was ahead in both benchmarks and that the repetition gave nearly the same total. A possible explanation is that a plan written before the first edit makes the model survey the affected code once. That is a conjecture; the measurement only shows fewer broken tests.

Delegation trades in the other direction. A sub-agent reads files in its own conversation and returns only its findings, which keeps the main conversation small. Each delegation is also a model run of its own. In round 4, both configurations used the plan prompt and ran at the same time with the same build:

Polyglot, 64 tasksWith sub-agentsWithout the task tool
Solved5954
Tool calls2,8901,323
Average seconds per task59.342.5

Without sub-agents the runs needed less than half the tool calls and solved five tasks fewer. Which side of this trade is right depends on whether you pay more for a failed task or for the additional calls. The comparison also holds only for these short tasks, where the second arm made no swarm calls either. On the longer SWE-bench tasks the agent without the task tool built a swarm at run time instead, so that arm did not measure the absence of delegation.

11. Observation: how you find out what happened

The measurements above were possible because the harness reports what it does. Every stage publishes events: a step begins, a tool is called, a result arrives, the context is rendered. With --trace DIR, a run writes them to a file, and agentkit viz displays them.

agentkit --trace .agentkit/trace --verify "Fix the failing test for empty input."
agentkit viz --open

The first command needs a configured model and a workspace with such a test; the placeholder task stands for your own. The trace contains the file contents and command output the agent saw, so treat it like the source itself.

For scripts, the executable reports the kind of ending through its exit code. This lets a calling program react without parsing text:

Exit codeMeaning
0The run ended with an answer.
1Runtime error, including a reached step limit.
2The model API or the network failed after the attempts described above.
3The context was too large or the prompt invalid.
4A required output format could not be produced.
124The run exceeded --timeout.

Exit code 0 states that the harness received a final answer. It does not state that the answer is correct. That is the reason for the checks in section 9, and for running your own tests afterwards.

Observation has limits of its own. The first analysis of the delegation experiment counted calls to task and reported zero delegations for the arm without that tool. A later look at all tool names found several hundred swarm calls in the same runs. The trace had contained them all along; the evaluation had searched for one name.

12. What to take away

The harness in agentkit consists of loop control, instructions with skills, context management, a tool layer with its permission rules, a few checks before finishing, and the reporting of events. Loop control and the tool layer mainly decide reliability: whether a rate limit, a torn stream, a hanging command or an interruption ends the work or is absorbed. Context management and skills mainly decide cost, through the size of every request, and context management decides what the model can still see late in a long run. The permission rules decide what a mistaken request can change. The finishing checks, the prompt strategy and delegation affect whether tasks get solved, and each of them was shown here to cost steps, time or solved tasks when set the wrong way.

Four limits apply to all of this. Most interventions are messages to the model, and a model can ignore a message. The permission rules restrain a model that errs and do not isolate untrusted code; that needs a container or a virtual machine. The benchmark numbers come from one small model and from task sets where repeated runs of one configuration differed noticeably. And several effects described here, such as the saving from skills or from a cached prompt prefix, follow from the construction and have not been measured.

If you want to examine your own runs, start with --trace and the trace viewer, then compare a run with and without --verify or -s plan on a task you know well. The loop with all rules from this article is in agent.rs; the article on sub-agents covers delegation in more detail.
