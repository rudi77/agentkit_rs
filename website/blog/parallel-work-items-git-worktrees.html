Running several work items at once: parallel workers and Git worktrees

Suppose a command-line tool has three report commands, and each should get a --json option. The three changes touch different files and do not build on each other. A work project that handles them one after another spends most of its time waiting for model responses that could have been requested at the same time.

Since the pre-release 0.33.0-rc.4, agentkit work run accepts --parallel N and can run up to N items at once. This article explains what determines how many items actually run together, why agents that change files need separate checkouts of the repository, and how their results end up on your branch. It assumes you know what a work item and an attempt are; Resume a longer project introduces both. You should also be familiar with Git branches and merges.

The commands below were not run against a real model for this article. The behavior described is covered by the runtime's offline tests, which use a scripted model. The section on costs and limits says what that leaves unmeasured.

1. The plan decides how many agents are busy

A work project starts with an objective. On the first run, a planning item asks the model to split that objective into items and to declare which items depend on which. For our example, a reasonable decomposition has four items. A real model may choose a different one.

ItemTaskDepends on
W-2Add --json to the export command—
W-3Add --json to the stats command—
W-4Add --json to the audit command—
W-5Document the new option for all three commandsW-2, W-3, W-4

W-1 is the planning item itself. An item can start once all of its dependencies are completed. W-2, W-3 and W-4 are ready immediately; W-5 has to wait for all three. The number you pass to --parallel is therefore an upper limit. With --parallel 8, this plan still runs three agents and then one, and a plan that is a chain of ten items runs one agent at a time regardless of N.

The runtime computes this shape for you. An item's stage is the length of the longest dependency chain leading to it, and the fullest stage gives the number of items that can run at once. agentkit work status and the plan approval print one line for it. The command-line output of agentkit is German; for our plan it reads:

Bis zu 3 Items gleichzeitig, 2 Stufen nacheinander.

That is "up to 3 items at once, 2 stages in sequence". The count is a deliberate simplification. It is accurate when the items of one stage take about equally long, and it is meant as a guide for choosing N. The implementation is plan_shape in state.rs.

Because the plan sets the limit, the planning prompt now tells the model how the items will be executed: several agents work at the same time and cannot see each other's changes. It asks for independent work to be placed in items without dependencies, and for items that change the same files to depend on each other even when they are logically separate.

2. One coordinator and several workers

The thread that runs agentkit work run acts as the coordinator. It asks the scheduler which item may start next, and it claims that item by appending a record to the project's journal, the file that holds the project's state as one JSON record per line. Then it starts a worker: a thread that builds a fresh agent for this one attempt, runs it, and records the outcome.

The order of these steps matters. The scheduler is a function of the recorded state and nothing else. If workers claimed items themselves, two of them could ask at the same moment and receive the same item. Since only the coordinator claims, and it writes the claim before it asks again, the next decision already sees the item as running.

Each worker has an identifier, worker-1 to worker-N, which the journal stores with the attempt. agentkit work status and agentkit work watch list every running item. All workers are threads of one process, started with Rust's scoped threads, so none of them outlives the run. There is no thread pool and no async runtime. With the default of one worker, the attempt takes the same path on a single worker thread. The code is in runner.rs.

3. Why two writers cannot share a directory

In an ordinary work project, every agent works in the same workspace directory. If the agents for W-2 and W-3 ran there at the same time, each would see the other's half-finished edits. A test run started by one could fail because of a file the other is still changing, and a failed attempt could not be undone without also discarding the other agent's work.

The scheduler therefore applies a rule when Git isolation is off: at most one item that writes to the workspace runs at a time. Whether an item writes is decided by its kind. Review and planning items only read, so they may run next to a writer. All other kinds, including analysis and documentation, count as writing, whether or not a particular attempt changes a file. Deciding by kind keeps the scheduler's choice independent of what an agent happens to do.

For our three implementation items, this rule means that --parallel 3 alone would still run them one after another. The status line says so when the plan allows more than one item at once and the project has no isolation. To run writers together, each needs its own copy of the files.

A second rule concerns the planning item. It runs alone. The items it creates do not depend on it and would be ready at once, so another worker could begin executing a plan that the planner is still extending.

4. A branch and a worktree for each item

Git can attach several working directories to one repository. Each such worktree has its own checked-out branch and its own files, while commits and branches are shared. A project created with --git-isolation uses this for every writing item:

  • The item gets a branch named work/<project-id>/<item-id>.
  • The branch is checked out in a worktree at .agentkit/work/<project-id>/worktrees/<item-id> inside your workspace.
  • The item's agent works in that directory. Your own working directory is not touched until the final merge.

An item without dependencies starts from the commit that was checked out when you created the project. A dependent item needs more: W-5 documents code that exists only on the branches of W-2, W-3 and W-4. Before W-5's agent starts, the runtime merges the branches of its completed dependencies into W-5's branch. If those branches contradict each other, the attempt fails with a merge conflict before any agent runs.

What happens after the attempt depends on its outcome:

OutcomeWhat the runtime does in the worktree
Success with changesCommits everything except .agentkit to the item's branch and records the commit as an artifact of the attempt
Success without changesCreates no commit and notes that fact
Failure or interruptionDiscards the changes and returns to the attempt's starting point, so that a retry begins clean

A worktree is a full checkout, including any build output the agent produced. The runtime removes it once no further attempt of that item is due. The branch remains, because the final merge needs it and the recorded commit refers to it. The Git operations are in git.rs.

Isolation is used with one worker as well. An earlier version switched branches inside your working directory instead; that could never support two writers, and keeping both mechanisms would have meant two code paths for the same result.

5. Merging the branches at the end

When every item has reached a final state, the runtime creates an integration item. No agent runs for it. The runtime itself merges the branches of all completed writing items into the branch you started from, in the order the items were created, with one merge commit per branch.

The merge into your branch needs a clean working directory. The runtime checks this when the run starts and again immediately before the integration, and it ignores its own .agentkit directory in that check. You may keep working in your directory during the run, as long as your changes are committed before the integration.

The runtime does not attempt to resolve conflicts. If two branches change the same lines, it aborts the merge, marks the integration item as failed with the affected files in the message, and the run ends as blocked, even though each item succeeded on its own. The decision of how to combine two conflicting changes is left to you. The item branches still exist at that point, so you can merge them by hand.

6. Running the example

You need agentkit 0.33.0-rc.4 or later with a configured model (see Get started), and a Git repository with a checked-out branch and no uncommitted changes. Run the commands in the repository's directory. The objective is an example; use one that fits your project.

agentkit work create --git-isolation \
  --title "JSON output for reports" \
  --objective "Add a --json option to the export, stats and audit commands and document it."

The command prints the project identifier, which is derived from the title. The following commands use PROJECT as a placeholder for it. Git isolation is chosen here and cannot be changed later.

agentkit work run PROJECT --mode plan
agentkit work approve W-1 -p PROJECT
agentkit work run PROJECT --parallel 3 -y

The first run stops after the decomposition and shows the proposed items with their dependencies, acceptance criteria and the status line from section 1. This is the moment to check whether items that will touch the same files depend on each other. agentkit work reject W-1 -p PROJECT --reason "…" requests a new decomposition instead. The last command runs the plan with up to three workers. The value is stored in the project's budget and applies to later runs as well.

-y approves the agents' shell commands automatically. Without it, each agent asks before a shell command. The questions are shown one at a time, but the prompt does not say which item is asking, so an allow list or -y is the more practical choice for a parallel run. Decide this as you would for any unattended agent run.

In a second terminal, agentkit work watch PROJECT shows the running items and their workers. When the run has finished, git log --graph on your branch shows the merge commits of the integration.

7. Stopping and failures

With several attempts in flight, the runtime has to decide what happens to the others when one of them ends the run. It follows one rule: a condition that prevents new attempts from starting does not abort attempts that are already running.

  • Budget exhausted, approval required or run blocked. The coordinator starts nothing new, waits for the running attempts and then pauses or ends the run.
  • A hard error in one attempt, for example in the configuration or in a Git operation. The other attempts finish and are recorded; then the first error is reported.
  • Ctrl-C. All agents observe the same cancellation flag and stop. Each attempt is recorded as interrupted, which does not count against the item's attempt limit. agentkit work resume PROJECT continues all of them.

A second Ctrl-C, or a killed process, ends the program without cleanup. The worktrees of the running items and the project's lock file remain. Your working directory is unaffected. The next run with --force takes over the lock, releases the interrupted items and reuses their worktrees after discarding the uncommitted changes in them.

8. Costs and limits

Parallel workers shorten the waiting time only where the plan has independent items. They do not reduce model usage; N agents send requests at the same time, and each has its own system prompt and context. The workers do not share a rate limiter. Each agent retries a rate-limit response on its own with a growing delay. How well this holds up for larger N has not been measured: the feature is tested offline with a scripted model, and nobody has yet compared run time, rate-limit responses and merge conflicts between --parallel 1 and --parallel 4 with a real model.

Some properties follow from the worktrees:

  • Conflicts appear late. Two parallel items that change the same place each succeed and collide only in the integration. The dependencies in the plan are the only protection, which is why reviewing the plan with --mode plan is worthwhile.
  • Only committed files are present. A worktree contains what Git tracks. A local configuration file or an AGENTS.md that is not committed is invisible to the item's agent, including any rules it contains.
  • Each worktree builds from scratch. In a Rust project, every item has its own target directory, so its first build is a full build and uses the corresponding disk space.
  • Reviewers do not see the diff. A review item runs outside the item's worktree and receives the attempt's artifacts and acceptance criteria. Code that exists only on the item's branch is not visible to it yet.
  • Branches accumulate. Item branches are kept after the merge and are not cleaned up automatically.

Two limits concern the workers themselves. An attempt that stops producing events keeps its worker slot until it ends; there is no watchdog that frees it during the run. And all workers belong to one process on one machine. The project's lock file continues to prevent a second process from running the same project.

9. Summary

The dependencies between work items determine how many agents a project can keep busy, and --parallel N sets an upper limit on top of that. One coordinator claims items in the journal and starts a worker thread per attempt. Items that change files run together only under Git isolation, where each works on its own branch in its own worktree. A dependent item starts with its predecessors' branches merged in, and a final integration step merges all item branches into yours or stops at the first conflict.

The work README (in German) documents the design decisions and open points in full. The offline tests in tests/parallel.rs show each rule from this article as an executable case.
