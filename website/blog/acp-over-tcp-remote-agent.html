Running the agent on another computer: the editor protocol over TCP

You edit on a laptop, and the project lives on a workstation: the checkout, the build tools and the test data are there. An agent that should read those files and run those tests has to run on the workstation. Its answers and its questions should still appear in the editor in front of you.

agentkit 0.33 supports this arrangement. This article explains how an editor normally talks to agentkit, what changes when the agent runs elsewhere, and what travels over the network. It follows a small test on one computer and then covers the directory rules and the security limits. It assumes you have used a terminal and know what a TCP port is.

1. How an editor talks to an agent

Editors such as Zed use the Agent Client Protocol, ACP for short. The editor starts the agent as a child process and exchanges messages with it through the process's standard input and output. Each message is one line of JSON. The editor sends requests such as initialize, session/new and session/prompt. The agent sends back its answer text, its tool calls and, before a shell command, a request for permission that the editor shows as a dialog.

agentkit acp is this child process. Because the editor starts it, the agent runs on the editor's computer and works on the files there. For the laptop and the workstation, that is the wrong computer.

2. A bridge and a server

The protocol itself does not care how its lines travel. agentkit therefore splits the child process into two processes connected by TCP. On the workstation, a server waits for connections and runs the agent. On the laptop, the editor starts a bridge, which connects to the server and copies bytes in both directions.

# on the workstation
agentkit acp --listen 10.8.0.5:7777 -w /srv/projects

# the command configured in the editor on the laptop
agentkit acp --connect 10.8.0.5:7777 --dir my-project

Replace 10.8.0.5:7777 with an address and a free port of the workstation. -w names the root directory below which sessions may work, and --dir names a directory below that root.

For the editor nothing changes: it still starts a program and speaks ACP with it. For the agent little changes: it still reads lines and writes lines. The work is in the short exchange that happens before the first protocol line.

3. One line before the protocol

A server that runs an agent for anyone who connects would hand out file and shell access to the whole network. The server therefore expects proof that the caller is allowed to connect. It also needs to know which directory the session should use, because the editor's project path exists only on the laptop.

Both pieces travel in a preamble: one line of JSON that the bridge sends as soon as the connection is open. The server answers with one line. After a positive answer the bridge forwards bytes without interpreting them.

bridge → server   {"agentkit_acp":1,"token":"…","dir":"my-project"}
server → bridge   {"ok":true}

The token is a random value of 256 bits. The server creates it on its first start in ~/.agentkit/acp-token and prints the file's path. The bridge needs the same value, either in the same file on the editor's computer or in the environment variable AGENTKIT_ACP_TOKEN, which takes precedence on both sides. A wrong token, an unknown preamble version or a preamble longer than 4,096 bytes ends the connection with {"ok":false,"error":"…"}. A client that connects and sends nothing is dropped after ten seconds.

The preamble is placed before ACP on purpose. ACP has an authenticate request of its own, but using it would require the bridge to understand the protocol. With a preamble, the bridge only has to copy bytes once the answer is positive. The code is in acp_netz.rs.

4. A test on one computer

You can try the mechanism without a second computer by letting server and bridge meet on the loopback address 127.0.0.1. The following test used agentkit 0.33.0-rc.6 on Windows with Git Bash. It needs a configured model, because the server builds an agent for each session. The token is set through the environment so that the test does not create a token file:

# Bash, terminal 1: the server; the current directory is the root
export AGENTKIT_ACP_TOKEN=test-token-1
agentkit acp --listen 127.0.0.1:47811 -w .

# Bash, terminal 2: the bridge, fed with two requests by hand
export AGENTKIT_ACP_TOKEN=test-token-1
{ echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":1,"clientCapabilities":{}}}'
  sleep 2
  echo '{"jsonrpc":"2.0","id":2,"method":"session/new","params":{"cwd":".","mcpServers":[]}}'
  sleep 3
} | agentkit acp --connect 127.0.0.1:47811

The server reported that it listens and that it took the token from the environment variable; its messages are German. The bridge printed two response lines. The first named the agent and its version, the second contained a session identifier and the three session modes that agentkit offers to an editor:

{"id":1,"jsonrpc":"2.0","result":{"agentCapabilities":{…},"agentInfo":{"name":"agentkit","version":"0.33.0-rc.6"},"authMethods":[],"protocolVersion":1}}
{"id":2,"jsonrpc":"2.0","result":{"modes":{"availableModes":[…],"currentModeId":"nachfragen"},"sessionId":"…"}}

The output is shortened at the places marked with an ellipsis. The same two requests sent to a local agentkit acp produced the same two lines, which is what copying bytes should achieve. With a different token on the bridge's side, the bridge printed an error naming a wrong token and ended with exit code 2, and the server logged the rejected address.

This test stops after session/new. It shows the connection, the preamble and the creation of a session. A complete prompt with tool calls and a permission dialog needs an editor, or a client that answers the agent's permission requests.

5. Setting up two computers

On the remote computer, start the server with the root directory and any options you would give agentkit acp, such as the provider or the model. The model configuration and credentials are read there.

# Bash, on the remote computer
agentkit acp --listen 127.0.0.1:7777 -w /srv/projects

Copy the token from ~/.agentkit/acp-token on the remote computer into the same file on the editor's computer. Then register the bridge in the editor. In Zed, this goes into settings.json:

{
  "agent_servers": {
    "agentkit-remote": {
      "command": "agentkit",
      "args": ["acp", "--connect", "127.0.0.1:7777", "--dir", "my-project"]
    }
  }
}

The example binds the server to 127.0.0.1, so only programs on the remote computer itself can reach it. An SSH tunnel carries the port to the editor's computer. Replace workstation with the remote computer's host name:

# on the editor's computer; keeps port 7777 forwarded while it runs
ssh -N -L 7777:127.0.0.1:7777 workstation

The bridge then connects to its own 127.0.0.1:7777, and SSH encrypts the traffic between the two computers. The user manual (in German) also describes running the server on Windows as a scheduled task.

6. Which directory the agent works in

An editor sends its project directory with session/new. On the laptop that may be /Users/me/code/my-project, a path the workstation does not have. The server therefore decides the working directory by these rules:

  • If the bridge was started with --dir, that directory is used for every session of the connection. A relative path is resolved below the root given with -w.
  • Without --dir, the editor's directory is used. This only works when the same path exists below the root on the server.
  • The directory must already exist and must lie below the root. Otherwise the server rejects the session and names --dir as the way out. It never creates a directory, so a client cannot decide where new directories appear on the server.

Each connection is served on its own thread and has its own sessions. Several editors can connect to one server and work in different directories below the root.

7. Security and limits

The connection is not encrypted. The token and everything the agent reads and writes cross the network as plain text. Bind the server to 127.0.0.1 and use an SSH tunnel, or bind it to the address of a VPN interface or of a network you trust. The server listens only on the address you give it.

The token grants what the agent can do. Whoever has it can read and change files below the root and, after approval in their editor, run commands on the remote computer. A server started with -y runs commands without asking. Start the server under an account with the rights the work needs and no more.

A session ends with its connection. When the connection closes, the server cancels the running task and ends the sessions; they cannot be resumed. If a connection breaks without being closed, for example because the laptop went to sleep, the server notices this only when it next writes to it.

Configuration is split. The model, credentials, .mcp.json, installed skills and plugins all come from the remote computer. A plugin command can serve as the remote agent: agentkit run NAME acp --listen … starts the server with that command's system prompt.

8. Summary

An editor speaks ACP with a child process over standard input and output. To run the agent on another computer, agentkit places a bridge at the editor and a server at the project. The two exchange one preamble line with a token and a directory, and from then on the bridge copies bytes. The server confines sessions to directories below its root, and the connection needs a tunnel or a trusted network because it is not encrypted.

The capability guide places this next to the other ways of calling agentkit, and agentkit 0.31: calling the agent from scripts, CI and other tools introduces the local editor integration.
