agentkit 0.31: calling the agent from scripts, CI and other tools

Suppose you have staged a change and want a second opinion before you commit it. You would like a plain yes or no from the shell, the same check on every pull request, and ideally the option to ask from your editor or from another coding assistant. Version 0.31.0 adds the pieces for each of these places.

This article follows that single change through the new features. It starts at the command line, moves to GitHub Actions and to other programs that start agentkit as a child process, and then covers the controls and robustness fixes that matter once runs become unattended. It assumes you have run agentkit at least once; the getting-started guide covers installation and model configuration. The commands below are taken from the user manual and README of this release. They were not executed against a real model for this article, so the exact answers you see will differ.

1. A yes/no answer in the shell

Before 0.31, a script could already pipe text into agentkit and read the final answer from stdout. Deciding what to do next still meant parsing that answer. The new --check option turns a question into an exit code: 0 means yes, 1 means no, and the model's reasoning goes to stderr. stdout stays empty, in the same way as grep -q. That makes the answer usable with &&, if and set -e.

# Bash: commit only if the staged diff passes the check
git diff --cached \
  | agentkit --tools none --check "Is this diff free of secrets and debug output?" \
  && git commit

Two details in this command are new. --tools none sends the diff to the model without any tools, MCP servers or project instructions. The model can only read what it was given and answer, so the call is shorter, cheaper and never asks for permission to run a command. --tools also accepts a list, such as read_file,grep or the group read_only, when the agent should be allowed to look at more of the repository. Internally, --check asks for a fixed JSON structure with a verdict and a reason, which agentkit then converts to the exit code.

If the same check should be available under a short name, you can save it as a custom command. A file ~/.agentkit/commands/NAME.md holds settings in its frontmatter and the system prompt below it. You run it with agentkit run NAME, or through a symbolic link to the agentkit binary with that name.

---
tools: none
check: true
---
Answer whether the diff on stdin is free of secrets and debug output.

Saved as ~/.agentkit/commands/secret-check.md, this becomes git diff --cached | agentkit run secret-check. The frontmatter keys are the same as in a --profile file; flags given on the command line take precedence over both.

2. Many inputs, structured output and patches

Once the diff passes, you may want to go one step further: describe each changed file, extract data in a fixed format, or let the agent propose an edit without touching your working tree. Each of these has a dedicated option.

One task per line. With --each, every non-empty line on stdin becomes its own task. {} in the prompt is replaced by the line, and -j N runs N tasks at the same time. The output is JSON Lines (one JSON object per line) in input order, with the fields index, input, exit, result and usage.

git diff --cached --name-only \
  | agentkit --each -j 4 --tools read_file "Summarise the change in {} in one sentence" \
  > summaries.jsonl

A fixed JSON shape. --schema FILE requests an answer that matches a JSON Schema. When the schema meets the provider's rules for strict output, agentkit asks the provider to enforce it directly. Otherwise agentkit validates the answer itself, sends the violations back to the model and retries. If no valid answer arrives, the run ends with the new exit code 4. The validator in schema.rs covers a subset of JSON Schema and adds no dependency.

Changes as a diff. --patch lets the agent work on a copy of the workspace. When it finishes, agentkit compares the copy with the original and writes a unified diff to stdout, which git apply accepts. The agent's text answer goes to stderr. In a Git repository, the copy contains the files Git tracks or does not ignore.

agentkit -y --patch "Replace println! with log::info!" > fix.diff
git apply --check fix.diff && git apply fix.diff

The copy protects your files from the file tools. Shell commands also run inside the copy, but run_shell is not sandboxed and can still reach anything your user account can. Review the diff before applying it.

The remaining options support these uses:

OptionWhat it does
--format stream-jsonWrites every event as a JSON line, followed by a final result record. Useful when another program wants to display progress.
--cache DIRReturns a stored result for an identical request without calling the model again. Only successful runs are stored. The cache does not see changes in the workspace, so it fits --tools none best.
--timeout DURATIONStops the run after, for example, 30s or 5m and exits with 124, the code timeout(1) uses.
-f FILE, -o FILE, -qAttach a named file as context, write the result to a file, and silence stderr completely.

The user manual lists all exit codes and shows further combinations (in German).

3. The same check in GitHub Actions

A check that only runs on your machine is easy to skip. The repository now contains a composite GitHub Action in action.yml. It downloads the release binary for Linux or Windows runners, runs a prompt and makes the answer available as the step output result. It also writes the answer to the job summary and, if you set comment: "true", posts it on the pull request or issue that triggered the workflow.

The following workflow is a shortened form of the review example that ships with the release. It requires a repository secret named ANTHROPIC_API_KEY.

on:
  pull_request:
    types: [opened, synchronize]

permissions:
  contents: read
  pull-requests: write

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: rudi77/agentkit_rs@main
        with:
          provider: anthropic
          anthropic-api-key: ${{ secrets.ANTHROPIC_API_KEY }}
          allow-shell: "false"
          token-limit: "400000"
          comment: "true"
          prompt: |
            Review the changes origin/${{ github.base_ref }}..HEAD.
            Report only real problems, each with file, line and reason.

fetch-depth: 0 gives the agent the base branch so it can compute the diff. allow-shell: "false" keeps this review read-only: the Git tools and read_file work without a shell. A second example, issue-fix.yml, lets a label on an issue start a run that opens a pull request with a fix. The action passes all inputs to its script through environment variables, so text from a pull request title or prompt is not spliced into shell code. The version input pins a release tag; the default latest takes the newest published release.

4. Starting agentkit from another agent or an editor

Sometimes the program that wants the second opinion is itself an agent, or an editor with an assistant panel. Two new subcommands let such programs start agentkit as a child process and talk to it over stdin and stdout.

agentkit mcp-serve runs agentkit as a server for the Model Context Protocol (MCP), the protocol many coding assistants use to call external tools. By default it offers one tool, agentkit, which takes a prompt, builds a fresh coding agent in the given workspace and returns its final answer. With --expose-tools, the agent's own file and Git tools are offered as well, and with --graph also the knowledge-graph tools. For Claude Code, registering it looks like this:

claude mcp add agentkit -- agentkit mcp-serve -w /path/to/project

Replace /path/to/project with the directory the agent may work in. Because stdin belongs to the protocol, agentkit cannot ask for permission before a shell command. In this mode run_shell therefore only runs programs on the allow list in ~/.agentkit/config.json, unless you start it with -y.

agentkit acp implements the Agent Client Protocol, which editors such as Zed use to host an agent. The editor shows agentkit's answer, each tool call and the plan, and it displays shell permission requests as a dialog. Each editor session gets its own agent in the editor's project directory and keeps its history across messages. MCP servers that the editor sends along are not yet passed through; agentkit loads its own .mcp.json.

{
  "agent_servers": {
    "agentkit": {
      "command": "agentkit",
      "args": ["acp", "--provider", "anthropic"]
    }
  }
}

This snippet belongs in Zed's settings.json. Both subcommands subscribe to the same event stream that the terminal interface uses. The agent loop itself did not change for them; the loop article explains that event stream.

5. Controlling unattended runs

In the shell you can watch a run and press Ctrl-C. In CI, or behind another agent, nobody is watching. Version 0.31 adds three controls for that situation.

Measured token usage and a limit. OpenAI, Azure and Anthropic report how many tokens a call used at the end of the response stream. agentkit now forwards this as a token_usage event after every model call. The numbers appear in the trace, in the agentkit-viz viewer as a total per agent, in the title bar of the terminal UI and in the summary line of the CLI. --token-limit N stops a task cooperatively once the measured input and output tokens of all its agents together exceed N, and the process exits with 1. The CI example above uses this through the token-limit input. The check happens after a call reports its usage, so a run can end somewhat above the limit.

Hooks around tools. A hook is a shell command that agentkit runs before or after a tool call. The model does not need to know about it. A typical use is running a formatter and linter after every file edit:

{
  "post_tool": [
    {"matcher": "write_file|edit_file", "command": "cargo fmt && cargo clippy -q", "timeout": 120}
  ]
}

matcher is a regular expression on the tool name. The command receives the tool name, its arguments and, after the call, its result in environment variables. Exit code 2 before a call blocks it and gives the hook's output to the agent as the reason; exit code 2 after a call appends the output to the result, so the agent sees the lint errors and can fix them. These codes match the convention Claude Code uses. agentkit loads ~/.agentkit/hooks.json and the file given with --hooks. A hooks file inside a project is deliberately not loaded automatically, because hooks run commands without asking and a cloned repository should not be able to trigger that. Hooks apply to the file, shell and Git tools of the main agent, sub-agents, swarm members and work items; MCP and graph tools run without them.

Declared tool effects. Tools can now declare whether they only read or whether they change something. --dry-run, which blocks changing actions and only records them, uses this declaration. For MCP tools it comes from the server's readOnlyHint and destructiveHint annotations. Only tools without a declaration are still classified by their name.

6. Native Anthropic support

Earlier versions reached Claude models only through an OpenAI-compatible gateway. agentkit now talks to Anthropic's Messages API directly. Set ANTHROPIC_API_KEY (optionally ANTHROPIC_MODEL, ANTHROPIC_EFFORT and ANTHROPIC_BASE_URL) or select --provider anthropic. With --provider auto, Anthropic is chosen when neither Azure nor OpenAI is configured.

The direct connection makes three provider features usable. Prompt caching marks the stable beginning of the request so that the provider can reuse it on the next call. Thinking blocks from the model are sent back unchanged, as the API requires, and dropped when the history has been rewritten. The token usage includes the cached share. The conversation history stays in agentkit's existing internal format and is translated only when a request is sent, so the rest of the agent is unaffected. --schema uses Anthropic's native structured output where the schema allows it.

7. Longer runs lose less context

A long coding task fills the model's context window. agentkit then compacts the conversation: it asks the model for a summary of the older part and replaces that part with the summary. This release changes several details of that process that could make a long run forget its goal or fail.

  • The original task of the running job is kept word for word. The summary is structured and now includes which tools were called with which arguments.
  • Notes from an earlier compaction go into the next summary. Previously they could disappear at the second compaction.
  • If the summary call fails, the history stays unchanged. Previously an empty summary could replace it.
  • Long tool results keep their beginning and end, where error messages and totals tend to appear. run_shell divides the space between stdout and stderr.
  • When a response is cut off at the output limit, truncated tool calls are not executed and broken JSON arguments are reported to the model. A cut-off text answer is continued once, and a stream that breaks off mid-response is retried up to twice.
  • If the agent repeats an identical call that returns an identical result, it receives a note pointing this out.

These changes address specific failures seen in long runs. They reduce the information lost at each compaction; a summary still cannot contain everything the original conversation did. For tasks where the full record matters, the managed context of ctxman stores large results outside the prompt so they can be retrieved later.

8. Upgrading and next steps

Returning to the staged change from the start: in 0.31 you can check it in the shell with an exit code, run the same check on every pull request, ask for it from an editor or another assistant, and limit how many tokens an unattended run may use. The features share one approach. agentkit reads stdin, writes the result to stdout and reports the outcome through its exit code, so other programs can build on it.

An existing installation updates itself with agentkit --upgrade. New installations follow the getting-started guide. The full list of options is in the agentkit README and the user manual; the individual changes are listed in the commits since 0.30.2.
